## 1. 结论

程序已经具备较完整的账号身份校验、配置备份、登录重试、任务状态展示和自动战斗能力。主要问题集中在多次架构迁移后的衔接处：旧总配置、新发布快照、运行中的账号序列和界面编辑结果，没有始终遵循同一个生效边界。

本轮复现了 **11 项问题，其中 4 项 P1、7 项 P2**。应优先修复配置导入生效、删除回滚、运行快照和序列数量边界，再处理界面、备份和发布检查。当前证据不支持直接进行大规模重写；先修正这些共享路径，比增加新的服务层更有效。

严重程度：P1 表示会影响实际执行配置、数据一致性或程序启动，应优先处理；P2 表示特定条件下的功能缺陷或保护措施缺口。这里的级别是修复优先级，不是安全漏洞评分。

### R01：配置包导入成功后，运行仓库仍读取旧版本

位置：`src/account_config_bundle.py:535–612`；`src/account_repository.py:359–383`、`:169–174`。

`AccountRepository._publish_master()` 先调用旧格式导入，再发布 `configs/published/active.json` 指向的新快照。然而界面导入配置包直接调用 `AccountConfigBundleService.import_bundle()`，只替换总配置、工作投影、运行状态和任务偏好，不更新生效快照。仓库只要发现 `active.json` 就优先读它。

复现：先建立生效快照，把 A1 的无音区编号从 1 改成 2 后导入。结果为 `import.ok=True`、旧总配置编号为 2，但 `repository.load_profile(A1).tasks` 中仍为 1。重启也不会自动发布此次导入的新内容。

建议：把图发布作为账号配置导入和编辑共同的提交入口；导入成功必须意味着运行仓库已经能读到同一版内容。补充“已有 active 快照 → 导入 → 当前进程和新仓库实例读取”的集成测试。

### R02：删除账号失败后没有恢复 active 指针和镜像

位置：`src/account_repository.py:493–540`；`src/account_publish_service.py:209–216`。

删除事务保存的 `before` 仅覆盖旧总配置、工作文件、运行状态、任务配置和单账号状态。`_publish_master()` 已经更新 active 快照后，如果后续状态文件删除或后置检查失败，异常处理只恢复这些旧文件，没有恢复 active 指针及 `configs/accounts/` 镜像。

复现：在真实 schema-v1 发布链上注入后置检查失败。旧总配置中的 A3 和其运行状态文件都恢复了，但 `repository.list_profile_ids()` 中仍没有 A3。

现有 `TestAccountDeletion` 的失败回滚测试把 `_publish_master` 替换为单文件写入，无法覆盖这个问题；使用真实发布链的测试只覆盖成功删除。

建议：明确原子提交点。提交前异常应恢复所有权威状态；提交后镜像维护失败应报告“已生效，镜像待修复”，避免把成功提交伪装成完整失败。对 active 更新后、状态文件删除时、镜像失败时分别注入故障。

### R03：运行快照只保存了下来，没有驱动下一账号选择

位置：`src/task/MultiAccountDailyTask.py:564–578`、`:774–781`、`:2537–2552`、`:2594–2625`。

`create_run_snapshot()` 创建并保存 `_active_run_snapshot`；但 `_next_target_account()` 每次重新调用 `get_sequence_accounts()`，该方法又读取实时仓库和当前设置。后续日常方案绑定也重新加载配置。`SequenceRunSnapshot` 本身虽不可变，执行链却没有持续使用它。

复现：运行快照仅包含 A1，把实时序列改为 A3，下一账号返回 A3。故障不依赖 OCR 或窗口操作。运行中 GUI 更新通知即使延迟，也不能阻止已经发布到磁盘的编辑被任务读到。

建议：整轮执行使用一次确定的 `profile_ids`、顺序和账号配置；界面新发布版本留给下一轮。身份重新绑定或账号删除如果必须中断当前运行，应明确中断，不能静默替换执行对象。测试应调用生产的 `_next_target_account()` 和方案绑定，而不只测试快照对象不可修改。

### R04：创建超过十个序列后，任务构造会越界

位置：`src/task/MultiAccountDailyTask.py:76–77`、`:164–179`；`src/gui/SequenceManagementTab.py:123–126`；`src/config_integrity.py:335–351`。

`SEQ_ACCOUNTS` 只有十项，构造函数对全部序列 `enumerate()`，直接访问 `SEQ_ACCOUNTS[i]`。序列创建服务和总配置校验没有限制最多十个序列。

复现：使 `get_sequence_names()` 返回 11 个序列，任务构造在 `sub_configs` 数组索引处抛出 `IndexError`。初始化周边依赖被隔离，执行的是原始构造函数。

建议：已经有独立序列管理页，可以让任务只保留当前序列选择和动态成员展示，去掉十个固定槽位；若暂时保留上限，应同时在创建、导入、启动时提供一致的校验和可恢复提示。补测 0、1、10、11 个序列。

### R05：停用的备用识别名仍可命中生产兜底逻辑

位置：`src/task/MultiAccountDailyTask.py:589–651`；`src/account_identity.py:79–108`。

共享身份匹配器会检查 `task_config['备用识别名称']`。但共享匹配返回空后，生产任务再次使用 `_profile_identities()`，直接加入 `alternate_login_name` 和 `备用识别名称内容`，忽略停用状态。

复现：A1 保留合成备用名，但设置为“无”。共享匹配结果为 `None`，`MultiAccountDailyTask.match_profile_from_login()` 却返回 A1。

建议：统一使用共享身份候选生成逻辑；OCR 容错也必须在同一处实现，且保持歧义拒绝规则。补测停用后保留旧文本、重新启用，以及备用名与另一个账号冲突的情况。

### R06：账号切换测试页的目标账号始终读不到

位置：`src/task/TestAccountSwitchTask.py:90–111`。

`_get_profile_names()` 调用了未导入的 `get_default_service()`。`NameError` 被外围 `except Exception: pass` 吞掉，随后返回空列表。函数后面的旧文件读取分支也不会执行。

复现：模块中不存在该名称，直接调用方法返回 `[]`。Pyflakes 同样报告该位置的未定义名称。

建议：补齐正确依赖，或直接复用现有仓库读取入口；必要配置读取失败应有可见错误。增加使用真实 `_get_profile_names()` 的单账号选项测试。连续 A1/A3/A4 模式复用生产解析逻辑，这一缺陷主要影响下拉选项，不应据此断言所有切换测试都无法运行。

### R07：外置数据仓库中的有效配置备份无法恢复

位置：`src/config_backup.py:181–210`；`src/secure_backup.py:103–128`；`src/task/DailyTask.py:1218–1227`；`custom_ok/ok/gui/MainWindow.py:383–418`。

恢复校验把 `backup_dir.parent` 当成同时包含备份源和程序配置目标的唯一根目录。程序目录与自定义数据仓库是两个独立目录时，正常的恢复目标被判断为越界。另外，自动备份优先使用“数据仓库文件夹”，日常任务的恢复服务却只读旧的 `Config Backup Directory`。跨盘时，即使修改了校验，当前从备份目录创建 staging 后直接 `os.replace` 到配置目录也存在跨卷限制。

复现：`application/configs` 备份到 `warehouse/backups`，快照和预检有效，实际恢复被 `ValueError` 拒绝；无需真的跨盘即可复现。

建议：分别验证源属于选定备份目录、目标等于程序配置目录，统一路径解析；最终待替换目录应暂存在目标所在卷。补充自定义仓库、独立目录、跨卷以及路径关联检查。

### R08：容量清理无法删除旧备份时会持续重试

位置：`src/config_backup.py:347–363`。

容量超限循环调用 `shutil.rmtree(..., ignore_errors=True)`。文件被占用、权限不足等情况不会抛出异常，目录仍存在，下一轮又计算相同容量并选择同一目录，没有退出或进度检查。

复现：用不删除任何文件的函数模拟删除失败，同一个快照连续被选择三次；探针主动中止，避免真实死循环。实际清理逻辑没有重试上限。

建议：删除失败后记录并退出，或跳过该项并限制尝试次数；检测容量或候选数量是否减少。参考账号切换证据清理中遇到删除错误即退出的做法即可，不需要引入新的清理框架。

### R09：月卡时间的允许范围与实际实现不一致

位置：`config.py:177–182`；`src/task/BaseWWTask.py:130–143`。

帮助文字写明小时可选 1–24，实际直接调用 `datetime.replace(hour=hour)`，只接受 0–23。

复现：`Monthly Card Time=24`，调用 `set_check_monthly_card()` 抛出 `ValueError: hour must be in 0..23`。

建议：统一界面和文档为 0–23，或明确将 24 解释为次日 0 点并处理日期。补测 0、23、24 以及已过当天检查时间的情况。

### R10：发布包检查只拦截根级 configs

位置：`scripts/package_smoke.py:18–34`。

检查账号配置时只判断 `path.parts[0] == 'configs'`。ZIP 多了一层普通目录就绕过该条件，例如 `app/configs/account_master_config.json`。此外 EXE/MSI 仅检查文件类型，当前“package-smoke”并没有完成安装和启动验证。

复现：只包含上述合成路径的 ZIP 能通过 `inspect_distribution()`。这证明检查器存在缺口，不代表已经发布的安装包确实包含隐私数据。

建议：以构建产物的明确目录布局作允许列表，对任意层级的运行数据目录检查；对安装器补充解包后的文件清单或实际安装冒烟验证。增加嵌套目录测试，并让作业名称准确反映验证范围。

### R11：直接继承 BaseChar 的自定义角色不能再次即时替换

位置：`src/gui/CharacterCodeTab.py:421–463`；`src/char/CustomCharLoader.py:139–165`。

自定义加载器允许角色直接继承 `BaseChar`，这也是复制内置角色源码后修改的常见形式。但界面的 `_reload_live_char_code()` 使用 `isinstance(char, self.current_char_cls)` 筛选旧对象，其中 `current_char_cls` 是内置类。第一次换成独立的自定义类后，这个条件不再成立；再次保存时旧对象被跳过。

复现：当前角色为直接继承 `BaseChar` 的旧自定义类，加载器返回新自定义类，热替换结果仍为 0，原对象未变化。现有界面测试使用“继承内置类”的自定义代码，未覆盖这一形式。

可达范围：当前 `config.py['custom_tabs']` 为空，主窗口的五个项目页面也没有实例化 `CharacterCodeTab`。这是保留编辑功能被启用或直接实例化时可复现的缺陷，不是当前默认导航下能直接触发的故障。

建议：通过角色注册的稳定标识匹配需要更新的实例，或在安全的任务边界统一重新加载。补测“内置→自定义 v1→自定义 v2→内置”。角色工厂以后重新识别队伍时可以加载新类，因此应描述为即时热替换失效，而不是代码永久无法更新。

## 4. 值得优先实施的优化

| 优先级 | 优化 | 依据与预期收益 |
| --- | --- | --- |
| 高 | 每次业务操作只加载一次完整账号图 | `list_profiles()` 逐账号重新读图，`legacy_profile_projection()` 又调用两轮。合成的两个账号仅生成一次投影就进行了 7 次完整 bundle 校验；N 个账号按当前路径约为 `2N+3` 次。减少重复解析、哈希和磁盘读取，尤其有利于高频登录 OCR 和 GUI 刷新 |
| 高 | 把账号编辑、导入、删除收敛到一个发布事务 | 直接解决 R01/R02；保留兼容文件作为派生数据，减少“写入成功但运行未生效”的状态组合 |
| 高 | 完整接入运行快照 | 统一整轮账号顺序、身份候选和任务参数，解决 R03，并减少执行过程中的重复配置读取 |
| 中 | 证据采样先判断采样间隔，再复制图片 | `record_frame()` 在间隔检查前就 `frame.copy()`，即使这帧被丢弃也付出了拷贝成本。先判断时间即可减少这部分开销 |
| 中 | 证据缓冲同时限制内存字节数 | 当前最多 30 张原始帧，30 张 3840×2160 BGR 帧约 712 MiB，尚未算临时副本。可缩放日常采样帧，只为点击关键帧保留原尺寸；这个估算是容量计算，不是实测进程峰值 |
| 中 | GUI 中的备份、整图哈希、写盘移出主线程 | 账号保存和新建经过多文件校验、事务备份及 ACL 设置；在慢盘上可能表现为窗口卡顿。先收敛重复 I/O，再用现有 Qt 工作机制执行耗时部分 |
| 中 | 使用已验证版本作为配置缓存边界 | 在一次操作/一轮运行内复用已校验图；版本变化时重新校验。不要为提速取消哈希校验，也不要用永久缓存掩盖文件损坏 |
| 中 | 合并重复的版本说明来源 | `AboutTab` 内嵌长篇更新日志，另有 `更新日志.md`；当前验证只检查字符串存在。可从同一个受控文件生成界面内容，避免发布时人工同步三处 |
| 中 | 明确 Python 3.12 的运行要求和依赖锁定 | `BaseChar` 使用 `StrEnum`，README/setup 的“Python ≥3.9”表述不准确；OCR 依赖仍使用下界版本约束。源码安装、安装器和 CI 应使用一致的支持范围 |
| 低 | 清理不可达代码及过时适配 | `AboutTab.py:315–368` 位于无条件 `return` 后面，22 个未定义名称都在这段死代码中，不应当作 22 个可达崩溃；清理它、重复导入和已经不使用的动态服务名探测 |
| 低 | 对热点视觉计算做有测量依据的优化 | `rotate_arrow_and_find()` 每次旋转匹配 360 个角度；可以在实际使用路径测耗时后缓存旋转模板或先粗后细搜索。不要凭函数名就重写整个识别系统 |

## 5. 尚需验证或明确设计的事项

以下内容没有计入 11 项已复现缺陷：

- **启动/退出的进程归属**：`main.py:182–193` 按可执行文件名结束启动器，又按命令行路径子串结束 WebView。两份安装目录里存在同名启动器时，应验证是否会误关另一份，优先改用所属 PID/父子进程关系。
- **跨实例并发写入**：仓库锁属于单个 Python 对象，发布锁只在进程内生效，旧格式导入还使用另一把服务锁。两个独立入口或外部编辑器并发更新时，需要验证 CAS 比较覆盖了从读到提交的完整区间。
- **生效快照损坏后的回退**：仓库读 active 损坏会拒绝，但部分任务读取方法捕获异常后仍回退到完整性服务的旧 master/旧缓存。应明确是否允许这种降级，故障注入应覆盖实际 task 读取入口。
- **任务停止状态**：`TaskRunCoordinator.request_stop()` 直接把状态变成 stopped，本身并未停止框架线程；真实停止仍由 ok-script 的执行器和 `TaskDisabledException` 完成。不要把状态模型的单元测试当作输入已经停止的证明。
- **故障证据的隐私边界**：日志过滤器不会自动处理所有 `event.json`、截图和备份文件。切换证据包含账号上下文且截图使用尽力而为的模糊处理，应明确本地排错原件与可分享版本的范围。
- **完整备份的恢复范围**：当前主路径的完成记录仍通过 `ConfigIntegrityService` 写入 `configs/account_runtime_state.json`；仓库另外提供根目录 `运行状态/` 下的记录接口。它们不是同一个文件，备份和删除语义需要统一，不能在文档中当作已经完成迁移。
- **战斗边界**：`combat_once(wait_combat_time=0)` 的返回变量没有初始化；当前核查到的内置调用未传 0，应在未来使用这种调用形式前处理。角色长动作、按键松开、断线、冻结计时及多显示器 DPI 仍需实机回归。
- **替代推理后端**：当前默认走 OpenVINO，本机没有 `onnxruntime`；把 `use_openvino` 改为 false 后需要对应可选依赖。YOLO 的非正方形输入比例计算也需专门验证，默认 640×640 下不会暴露这类宽高颠倒。
- **手工更新包路径**：`打包更新.py` 仍打包部分本机 `.venv` 框架文件，而非完整 `custom_ok` 覆盖集。它与 CI 的安装器发布不是同一条管线，应核对跨版本更新时是否遗漏框架补丁。
