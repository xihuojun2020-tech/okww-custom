# A4 凝素领域连续失败：原因核验与解决方案

日期：2026-09-07。范围：分析与方案，不修改生产代码、不启动游戏、不发布新版本。

## 1. 结论

两次账号失败的直接原因均为：切换角色期间 `in_team()` 返回失败 → `raise_not_in_combat()` 抛出异常 → `combat_once()` 捕获该异常后正常返回 → 领域任务进入寻宝阶段 → 30 秒内找不到寻宝图标或领取交互，抛出 `WaitFailedException`，上层记录 A4 失败并继续序列。

已经确认的代码缺陷是**未区分正常战斗结束与状态异常，以及奖励阶段缺少明确状态门禁**。队伍识别失败的现场原因仍未确认：无截图，不能断言一定是角色动画、视觉误判、死亡或挑战结算。不能承诺单纯延长时间即可修好。

附件报告提出的“当前体力只有 2，所以不该继续挑战”忽略了第二轮 `allow_backup=True`；“in_team 固定 3.1 秒超时”也不符合代码。两项都不宜直接作为修改依据。

## 4. 代码问题与证据强度

### 4.1 单次队伍识别失败立即终止切人：确定存在，现场误判原因待验

位置：`src/task/BaseCombatTask.py:672`；检测实现：`src/task/BaseWWTask.py:1103`。

`in_team()` 在当前帧匹配 char_1_text/char_2_text/char_3_text，阈值0.8，仅匹配到1或2个时认可队伍。它没有3.1秒等待逻辑。切人循环一旦看到 False，就立即 `raise_not_in_combat()`；后面的 `switch_char_time_out` 判断、next_frame和continue不可达。日志耗时是 `now - start`，不等于单次识别耗时。

所以：瞬时 UI 不完整会进入异常路径，这是代码事实；四次现场是否属于瞬时 UI 缺失，材料不能证明。

### 4.2 异常结束被正常返回掩盖：确定缺陷，最高优先级

位置：`src/task/BaseCombatTask.py:391`。

`combat_once()` 对 CharDeadException 重新抛出，但对其他 NotInCombatException 仅记录日志，随后执行 combat_end、等待队伍恢复（失败不抛出）并返回进入战斗时的 result。该返回值不能代表战斗获胜。DomainTask 不检查结果，直接寻宝。

离线调用当前实际方法，注入 `NotInCombatException('not in_team while switching')`，方法返回 True，且调用 combat_end。此探针未进行游戏输入。

### 4.3 奖励阶段以负面信号代替成功证据：确定缺陷

位置：`src/task/DomainTask.py:99`、`:140`。

寻宝超时后 `_domain_combat_finished()` 接受 `_in_combat=False` 且无目标/无血条作为结束依据。但异常路径本身已经清除 `_in_combat`，菜单、加载、遮挡同样可能无目标。随后继续 pick_f/use_stamina，缺少领域奖励/领取/结算状态的明确确认。

离线探针证明：即使 is_expected_combat_end=False，只要另外三个条件满足，仍返回 True。两次最终异常表明超时后的复核没有通过，但日志没有记载究竟哪个视觉条件导致拒绝。

### 4.4 “2点体力仍继续”：本例不成立

位置：`src/task/BaseWWTask.py:535`、`src/task/DomainTask.py:56`。

使用当前实际 use_stamina 方法，以 current=82、backup=417、once=40、must_use=120 输入：

- allow_backup=True → 扣算80，返回 can_continue=True；剩2+417，预算还差40。
- allow_backup=False → 同样扣算80，但返回 can_continue=False。

因此不能增加“一律 current < once 就退出”的规则，否则会破坏已允许使用备用体力的流程。可加强领取成功确认、补充体力后的复读和失败退出，但这是核算可靠性改进，不是已证实的本次直接根因。

## 5. 建议修改顺序

### 第一步：修正战斗结束与奖励阶段的边界（P0）

1. 为非正常状态丢失保留可区分的异常/结果；不要让 combat_once 把这类异常转换成正常返回。保留正常目标消失、明确结束和死亡恢复的既有语义。
2. 领域调用者分别处理：有明确结算/奖励证据则领取；仍有有效战斗证据则有限恢复；状态不明则保存证据、停止本次流程。不得继续盲目寻宝、领取或再次挑战。
3. 未知状态恢复使用单独、有上限的次数与总时限，不直接复用“死亡已恢复”的返回值或日志。停止、窗口丢失和截图异常必须继续向外传播。
4. 梳理所有 combat_once 调用者：凝素/模拟领域、无音区、梦魇、刷声骸、地图、深塔。保持依赖原返回值的调用兼容，尤其不能把“曾进入战斗”偷偷改成“获胜”而不调整调用方。

### 第二步：切人过程允许短暂状态缺失（P1）

1. 在切人局部使用连续新帧确认，短暂缺失不马上宣称脱战；保留现有匹配阈值作为起点。
2. 缺失期间暂停盲发切人和普攻，检查明确结束、复活、有效窗口/帧及动画状态；不能仅凭“有目标框”就认定一定可切人。
3. 将超时检查移到实际可达位置，使用统一单调时钟预算。具体容忍时长用录像/回放验证，不直接全局扩大到6–8秒。
4. 不先改爱弥斯/琳奈/莫宁轮转；若现场证据证明某角色动画有专属边界，再做针对性处理。

### 第三步：可靠核算与现场诊断（P1）

1. 领取前确认确实处于对应奖励界面；确认领取成功后才计入 used stamina 和剩余预算。识别失败不得用默认扣费掩盖。
2. 再次挑战条件继续使用当前/备用策略和剩余预算；备用不足、禁止使用备用、预算完成分别正常退出。不要无条件要求当前体力>=40。
3. 在切人首次异常、恢复超时、奖励状态未知时保存限频证据：前后帧、三个队伍特征置信度、目标/血条、角色与切人方向、帧龄、窗口、结束原因、体力策略与实测/推算区分。避免额外逐帧日志和重复截图。
4. 包内没有现场帧不等于程序绝无截图能力；切人分支的截图调用当前被注释。复用现有证据保留/脱敏规则，让诊断导出明确说明是否包含图片。

## 6. 验收要求

- 短暂队伍UI缺失后恢复：继续正确角色，不误入奖励阶段。
- 长期缺失：有界停止/恢复，保留具体原因，不无限循环。
- 战斗结算、角色死亡、未知画面、仍有敌人：分别走对应分支；未知不能记为成功。
- 真正结算画面已出现但无寻宝图标：直接处理已确认的奖励界面，不白等30秒。
- current=2、backup=417 的允许/禁止备用两组；预算完成、备用不足、OCR失败、补充失败、领取未成功均覆盖。
- 停止任务在所有等待与恢复阶段有效；输入释放；未知结果不写账号完成记录，其他账号仍按既有隔离策略执行。
- 先补 TestBaseCombatTask、TestDomainRecoveryLoop、TestStaminaAccounting 的行为测试，再运行对应调用方与全量回归。现有部分测试把“无目标即结束”写成通过条件，需要同步更新预期，不能只新增测试而保留错误契约。
- 受控实机复测 A4 的爱弥斯/琳奈/莫宁队伍及所选凝素领域；记录动画/奖励画面、实际体力变化，避免离线通过后直接宣称实机根因解决。

## 7. 当前处理建议

暂不采用“把3.1秒改成8秒”或“体力<40无条件停止”的方案。若再次遇到失败，可先暂停自动重试，确认游戏停在战斗、奖励、菜单还是加载画面；保留切人失败前后约10秒的脱敏录像，对识别根因最有帮助。

本次已完成日志对照、源码版本比对和三组离线分支探针；未改生产代码、账号配置或游戏状态。离线结果在 `test_out/a4_forgery_20260907/offline_findings.json`。
