# 每日任务世界首领突破材料设计

状态：设计已整理，待实施。日期：2026-10-03（北京时间）。设计基线：1.92.02 / b5edc564。

## 1. 用户已确认的目标

在账号每日任务的体力模块增加“世界首领突破材料”。执行复用现有 `FarmEchoTask` 的“讨伐强敌 / Boss Challenge”流程，补充领取奖励与进度调度。

- 每个账号保存三个首领目标及累计领奖次数上限，依次按1、2、3执行。
- 只计成功领取奖励的次数；产出4个还是5个材料均不参与计算。
- 次数跨日、跨周和程序重启保留。
- 当前目标达标后切换下一个；同一运行有足够体力时可以连续完成多个目标。
- 全部启用目标达标后，按当前账号原有体力选择继续刷：凝素领域、无音区，或已有模拟训练选项。
- 单账号每日与多账号每日共享同一账号的配置和进度。
- 本文批准的是设计整理；程序实现、实机执行和版本发布尚未进行。

## 2. 配置位置与界面

“账号设置 → 体力与每日”中，增加“世界首领突破材料”区域，与现有无音区设置同属体力模块。默认模板也提供相同区域。

```text
世界首领突破材料（按优先级刷取）
1  [首领名称 / 无 ▼]  [ 6 ] 次   已领 2 / 6    [校正]
2  [首领名称 / 无 ▼]  [ 3 ] 次   已领 0 / 3    [校正]
3  [无 ▼]             [ 0 ] 次   已跳过

当前目标：优先级1，还需领取4次
全部目标达标后：跟随本账号体力用途（当前：凝素领域）

体力用途              [凝素领域 / 无音区 / 模拟训练 ▼]
对应关卡选择           [当前账号的现有配置]
```

### 2.1 字段规则

- 新字段：`World Boss Material Targets`，固定三行，行结构为 `{boss: 稳定首领ID或none, limit: 非负整数}`。
- 缺失字段或空列表视为三行“无 / 0”；旧账号因此默认关闭此功能。
- 上限范围0至9999；0跳过，不引入无限刷取选项。
- 同一账号三行中不能重复选择同一有效首领，避免累计进度重复归属。
- `Which to Farm` 等现有字段继续决定首领目标完成后的体力用途。新功能不是该下拉框中的第四个互斥选项。
- UI展示首领名称；持久化稳定首领ID。游戏列表序号仅用于导航提示，不能作为身份或计数键。
- 下拉目标仅来自经核对的“讨伐强敌”可领取突破材料首领目录；普通声骸目标、周本和未核对的新首领不混入。

### 2.2 累计上限语义

上限是这个账号对该首领的累计总目标。已领8次，新增需求3次，应把上限改为11；提高上限不会清空原进度。

改变排序、昵称、序列或暂时选“无”不会删除历史计数；再次选择同一首领继续读取该首领已有累计数。校正累计次数需明确确认，并保留操作历史。

不提供材料数量换算、仓库数量扫描或预估掉落计算。

## 3. 复用与职责

| 模块 | 责任 |
|---|---|
| `FarmEchoTask` | 保留并复用讨伐强敌选取、传送、地图移动、入战、战斗、复活、声骸拾取和再次挑战；提供一个可共享的单轮刷取方法 |
| `WorldBossMaterialTask(FarmEchoTask)` | 材料模式入口、战前资源检查、领奖处理、目标切换、体力交接 |
| `world_boss_materials.py` | 经核对的首领目录、稳定ID、名称别名与既有4C首领场景配置映射 |
| `world_boss_material_plan.py` | 三目标验证、选择下一个未达标目标、计划修订摘要 |
| `world_boss_material_progress.py` | 按账号UUID和首领ID持久化计数、待核验领奖事件及校正记录 |
| `WorldBossMaterialPlanWidget` | 三行编辑、只读累计数、校正与待核验入口 |
| `DailyTask` | 统一单账号/多账号调用，衔接原体力用途与活跃度补跑 |

复用周本的优先级交互和原子领奖记录模式；数据使用独立命名空间 `world_boss_material_claims:<profile_id>`。复用已有 `ConfigIntegrityService.get_progress/update_progress`，不新建数据库。

对 `FarmEchoTask` 的修改限于共享单轮流程和必要的处理钩子；不复制完整4C循环，不改角色轮转。材料任务有独立任务实例和临时执行参数，运行后清理，避免把目标/领奖模式写入原刷声骸任务的持久配置。

## 4. 每日执行顺序

保持现有周本检查、梦魇等每日阶段的顺序，在原“清理体力”位置插入首领材料阶段：

```text
核验账号身份
  → 执行现有每日前置及到期周本
  → 刷未达标的世界首领材料目标
      → 目标1完成 → 目标2 → 目标3
  → 首领目标全部达标 / 未配置 / 全部为0
  → 按本账号原有体力用途清理剩余体力
  → 完成既有活跃度检查、截图、录像和退出流程
```

若首领目标尚未达标但当前可授权体力不足，保存部分进度并结束这一轮体力处理。下次从未达标目标继续，不把“没体力”当作目标完成。

现有“养成材料规划”已启用时，首领材料优先执行；全部首领目标达标后继续原养成规划分支及其已有体力规则。该规划的库存统计不参与首领领奖次数判断。未启用养成规划时直接按 `Which to Farm` 选择后续任务。

正常清体力和 `_complete_missing_daily_stamina` 局部补跑调用同一个新入口 `_run_profile_stamina(config, activity_ready, used_stamina)`，都先检查首领计划，避免补跑绕开目标或重复领取。

多账号每日继续调用生产 `DailyTask`，账号选择、登录、验证和退出沿用原链路。

## 5. 一轮首领执行与领取

1. 核验当前账号UUID，读取最新计划、累计数和待核验记录。
2. 选择最前面的未达标目标，重新确认当次剩余次数。
3. 用现有F2“讨伐强敌”流程选取首领。名称核对成功后才传送；序号提示不匹配时按名称搜索列表，不能按旧序号直接消费。
4. 读取当前体力和该目标单次领奖费用，执行现有每日备用体力策略。不可授权单次领奖时，先结束，避免打完无法领奖。
5. 复用4C的战斗、场景交互、复活与移动；使用共享自动战斗循环。
6. 战斗后先确认奖励可领取，靠近奖励入口。声骸是否掉落或吸收成功不作为领奖成功条件。
7. 在发生可能消费的输入前，持久化待核验事件；检查失败则不发送领奖输入。
8. 确认领奖界面、费用、余额及当前目标未被用户关闭；执行一次单倍领取。
9. 确认成功结算/对应奖励页面；立即将事件标为confirmed，累计加1。
10. 再处理声骸拾取、结算关闭和资源复读；资源复读失败也不撤销已经确认的领奖数。
11. 读取新计划。还有欠数则走现有刷新/再次挑战路径；当前目标达标则切换下一目标；全部达标则交回每日体力入口。

### 5.1 现有取消弹窗的修正范围

目前 `BaseWWTask.handle_claim_button` 会ESC关闭领奖，`FarmEchoTask.on_combat_check`、`scroll_and_click_buttons`、宝箱/场景交互及异常恢复都可能调用它。

材料任务统一接管这些领奖处理入口。仅在已确认战斗结束、目标和账号正确的领奖阶段允许消费；其他阶段出现领奖界面应识别并交给材料状态机，禁止自动ESC取消或盲目确认。普通4C实例继续使用原声骸模式的处理方式。

材料模式的共享循环允许“不拾取声骸也进入领奖步骤”。不沿用声骸检测来认定材料任务成功。

### 5.2 单次领取口径

首版每轮只执行一次单倍领取，成功后记1次。双倍领取选项不用于材料模式，避免一次消费跨过只剩1次的目标。费用以当前目标界面为准，不能把凝素、无音区或周本费用直接套用。

复用已确认相同布局的现有领取组件；对单按钮确认等不同布局在材料任务内适配，不能直接按“左按钮/右按钮”的假设点击。

## 6. 领奖进度与中断

运行状态示例：

```json
{
  "counts": {"verified_boss_id": 2},
  "events": {
    "claim_event_uuid": {
      "boss": "verified_boss_id",
      "state": "confirmed",
      "plan_revision": "计划摘要",
      "count_before": 1,
      "cost": 60,
      "time": "UTC时间"
    }
  },
  "corrections": []
}
```

这里的60只是数据结构示例，不作为程序默认费用。

事件使用pending/confirmed/cancelled三种状态。重复确认同一event_id不重复加数。已确认领取写入应先于退出或下一次战斗。

若点击后结算结果未知、确认写入失败或进程中断，保留pending；停止该账号后续消费，在账号设置与完成检查提示“有一次材料领奖待核验”。用户核对后明确选择“已领取，计1次”或“未领取，不计数”。未知时不自动再次点击，不能由死亡次数/战斗次数推断领取结果。

账号导出、备份恢复和导入保留历史计数、事件与校正记录。同UUID恢复时采用不低于本机已确认计数的记录，同一事件按已终结状态优先，未核验事件保留；账号配置模板仅复制目标设置，不复制累计数。只有显式校正允许减少累计数。

每日04:00仅影响每日记录，首领累计数不清零。目标全达标后后续每日直接进入原体力用途；调整目标或提高上限后重新判断，不依赖旧“已完成”时间跳过新需求。

## 7. 体力与自动战斗联动

- 首领与后续凝素/无音区使用同一账号的 `DailyReservePolicy`。
- 每次确认领取后按实际核验的费用更新消耗；转入下一首领或后续体力任务前刷新当前体力、已消耗体力及活跃度。
- `daily_stamina_budget` 返回0表示没有备用体力补齐预算，不能据此禁止清理现有体力。
- 本轮已经达成活跃度或活跃度未知时，仍可消耗当前体力；备用体力授权继续遵循现有策略。
- 世界首领累计上限不授权使用星声、溶剂或额外恢复道具。
- 自动战斗保持既有启用意图；材料任务失败不能将后台 `_enabled` 写成False。前台首领战斗使用共享战斗循环，后台不同时发送输入。
- 用户停止、全局暂停、应用退出与账号身份/配置异常按现有边界处理。未确认领奖会阻止消费，但不清除自动战斗偏好。

## 8. 异常与可观察性

| 情况 | 行为 |
|---|---|
| 体力不足 | 保存已确认次数，显示待续；继续既有每日收尾，按真实活跃度判断每日完成 |
| 未解锁传送、首领名称不符、领奖费用未知 | 保存错误证据，停止材料消费；不能切换到其他首领或副本掩盖目标未执行 |
| 死亡或复活 | 复用4C恢复，不计领奖次数 |
| 有pending领奖 | 禁止该账号后续消费，展示核对入口；交由现有多账号失败收尾/下一账号策略 |
| 运行中修改计划 | 在消费前和一次领取保存后重新读取；已领取属于原首领，下一轮按新计划调度 |
| 领取成功后传送/退出失败 | 领奖次数已保存，不重复补领 |
| 配置或账号核验失败 | 按既有完整性机制中止，不能消费默认账号目标 |

信息面板显示：当前首领、优先级、累计/目标、剩余次数、阶段、实际本轮消耗、后续体力用途、待核验状态。

日志逐次记录首领ID、事件ID、领取前后累计、计划修订、资源核验和转入后续任务原因；采用现有脱敏机制。结算证据和错误截图进入现有 `okww监控室` 目录体系，复用存储服务，避免新建分散证据目录。完成检查展示材料进度，不把累计目标未达标直接等同于每日任务失败。

## 9. 验收与发布

离线测试覆盖配置校验、累计及恢复、重复确认、三个目标切换、有限上限、体力不足、凌晨04:00、改计划、后续选择、养成规划衔接、局部补跑、普通4C取消领奖回归、单/多账号共享及输入所有权。

使用端实机核对：一个大世界首领及一个走现有独立场景入口的首领，各至少确认单次材料领取、重复挑战、最后一次领取和切换后续凝素/无音区；有授权和对应目标时再验收跨首领同次运行。首领目录中的特殊入口适配需逐项验证；缺少验证证据的条目不标为已支持。

按中等功能版本发布：当前基线下拟1.93.00；若实施前已有新版本则按实际基线重算。修改代码时同步config.py、README和更新日志；验证后提交、创建匹配注释标签、推送GitHub并发布到唯一当前NAS。验证源码更新包不包含账号配置或监控证据。

当前交付仅设计文档，不进行功能版本号变更或发布。
