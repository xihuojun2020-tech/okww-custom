# 账号配置安全、便捷编辑与三层身份识别设计

日期：2026-08-26  
状态：待用户审核  
目标版本：1.17.01

## 1. 目的

本设计综合 ALAS 的独立实例文件、原子写入和配置校验经验，以及 okww
现有的 UUID、完整性指纹、修订冲突、备份、运行状态分离和事件留证机制，
建立一套同时满足以下目标的账号配置方案：

1. 修改一个账号时，其他账号配置不会被污染；
2. 用户可以在 UI 中方便地修改、导入、导出和移动账号；
3. 程序运行使用经过校验的完整快照，不读取正在编辑的半成品；
4. 异常退出、并发修改或配置损坏时可以恢复到上一个有效版本；
5. 账号的人类可读信息、扫码备用名称和游戏内稳定特征码职责分离；
6. 游戏内特征码暂不参与当前任务逻辑，为后续身份核验预留接口。

## 2. 三层身份模型

所有账号都必须拥有一个不可变的内部 `profile_id`（UUID）。三个业务识别
字段只作为不同场景的识别材料，不能互相替代，也不能作为序列的外键。

### 2.1 人类可读身份

字段建议：

```json
{
  "phone": "完整手机号（如确实可获得）",
  "masked_phone": "游戏界面显示的带星号手机号",
  "nickname": "游戏昵称",
  "display_name": "界面显示名称"
}
```

用途：

- UI 列表和日志中帮助用户知道当前是哪一个账号；
- `masked_phone`（例如中间带星号的手机号）是当前账号切换的关键识别依据，
  必须作为独立字段保留，不能在保存或导入时被还原、清洗或丢弃；
- 账号切换匹配优先使用 `masked_phone`，再结合昵称和其他候选名称消歧；
- 允许修改，不改变账号的 `profile_id`；
- 完整手机号、脱敏手机号和昵称均可能变化，不能作为唯一身份或序列引用；
- 完整手机号不得写入普通日志；导出预览和错误提示默认只显示 `masked_phone`。

### 2.2 扫码备用识别名

字段：`alternate_login_name`，格式通常为 `U` 开头、`A` 结尾。

用途：

- 手机号不可见或不可用时，作为账号切换的备用匹配条件；
- 用于登录页/账号切换流程的候选匹配，不作为最终可信身份；
- 该名称由手机或模拟器扫码流程产生，允许重新生成或变更；
- 变更时必须通过账号配置编辑器记录差异，不能静默覆盖。

### 2.3 游戏内稳定特征码

字段：`game_feature_code`。

来源：原版 okww 的防 OLED 烧屏遮罩区域。该遮罩区域会显示一个游戏内
识别码；这个识别码被视为游戏侧唯一且长期稳定的账号识别码。

当前阶段规则：

- 只保存和展示，不参与现有账号切换、每日任务或普通预检；
- 当前没有读取不到特征码就阻止任务的行为；
- 不允许用手机号或 `alternate_login_name` 自动填充该字段；
- 手工修改时必须显示高风险提示，并记录完整性事件；
- 后续启用游戏内身份核验时，任务开始前必须将检测到的特征码与该字段
  比对，不匹配就安全停止，不得继续执行账号任务。

当前账号切换的识别顺序为：

```text
带星号的 masked_phone（关键依据）
        ↓
昵称/完整手机号（辅助消歧）
        ↓
U...A alternate_login_name（备用匹配）
```

未来启用游戏内校验后的身份核验优先级为：

```text
游戏内特征码（最终核验）
        ↓
带星号的 masked_phone（账号切换关键依据）
        ↓
U...A alternate_login_name（备用匹配）
        ↓
手机号/昵称（用户识别和辅助消歧）
```

## 3. 文件分层

```text
configs/
├─ accounts/
│  ├─ profiles/<profile_id>.json   # 单账号可编辑文件
│  ├─ index.json                   # UUID、显示信息、别名和顺序
│  └─ sequences.json               # 序列只保存 profile_id
│
├─ published/
│  ├─ bundles/<revision>/          # 已验证的不可变运行快照
│  │  ├─ account_master_config.json
│  │  ├─ daily_profiles.json
│  │  └─ manifest.json
│  └─ active.json                  # 当前有效 revision 指针
│
├─ runtime/
│  ├─ accounts/<profile_id>.json   # 完成记录、游标、断点
│  └─ global.json
├─ backups/
└─ incidents/
```

`profiles` 和 `index` 是用户编辑层；`published` 是程序运行层；`runtime`
是程序状态层。自动任务不得直接写入编辑层或已发布快照。

## 4. 保存与发布流程

UI 保存一个账号时执行以下事务：

1. 读取账号当前 JSON、序列索引和基准 revision；
2. 显示字段级差异，手机号和识别信息默认脱敏；
3. 用户确认账号短名和修改内容；
4. 检查基准 revision，发现其他窗口修改时拒绝覆盖；
5. 校验 JSON、字段类型、UUID、别名冲突和序列引用；
6. 在临时 bundle 目录生成完整的新快照；
7. 对每个账号文件计算 SHA-256，并写入 `manifest.json`；
8. 完整校验通过后，原子替换 `active.json` 指针；
9. 将旧 bundle 保留到备份目录；
10. 重新加载不可变运行快照。

发布失败时，旧 `active.json` 仍指向完整旧版本。启动时发现残留临时目录，
只清理未提交的临时内容，不删除有效版本。

## 5. UI 设计要求

账号编辑页必须提供：

- 人类可读信息编辑：手机号、昵称、显示名称；
- 扫码备用识别名编辑和格式校验；
- 游戏内特征码只读展示（未来可由专用采集流程写入）；
- 当前账号任务参数编辑；
- 账号加入/移出序列；
- 差异预览、保存、导入、导出和恢复；
- 删除前显示所属序列、运行状态和备份信息。

删除账号采用“预览 + 输入显示名称二次确认 + 可恢复回收站”的流程；
删除序列只删除序列关系，不删除其中的账号。

中文字段解释放在 UI 帮助文本和保留的 `_comments` 命名空间中。`_comments`
和未知 `extensions` 必须原样保留，不参与任务字段解析。

## 6. 并发、完整性和隐私边界

- 使用进程内锁和跨进程发布锁；
- 使用 revision/CAS 防止旧草稿覆盖新配置；
- 使用 manifest 检测单文件被外部修改；
- 检测到编辑层和已发布层不一致时进入安全模式，不自动猜测；
- 运行状态只能通过明确的 `profile_id` 写入；
- 日志和事件目录不得记录完整手机号、密码或鉴权信息；
- 该设计保证配置隔离和可恢复性，不等同于账号秘密加密；如未来保存
  登录凭据，应另行使用 Windows DPAPI 或系统凭据存储。

## 7. 分阶段启用

1. 先实现三层身份字段、UUID 校验和只读展示；
2. 再实现单账号编辑、差异预览、备份和 CAS；
3. 再实现 bundle、manifest、active 指针和崩溃恢复；
4. 完成并发、强制终止、导入导出、删除恢复和账号切换测试后，
   才让所有任务默认使用已发布快照；
5. 游戏内特征码核验作为独立后续功能，启用前不得改变当前任务行为。

## 8. 验收标准

- 修改 A1 后，A3/A4 文件摘要和配置内容不变；
- 将 A3 从序列一移动到序列二时，只改变序列关系和发布快照；
- 两个窗口同时编辑同一账号时，后提交者收到冲突提示；
- 发布过程中强制终止后，程序只能恢复旧 bundle 或完整新 bundle；
- 删除账号后可从备份恢复，删除序列不会删除账号；
- 未填写游戏内特征码时，当前任务仍按现有逻辑运行；
- 未来启用特征码核验后，检测不匹配必须安全停止。
