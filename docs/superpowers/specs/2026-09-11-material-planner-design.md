# 鸣潮养成材料规划与收益统计：需求及设计

日期：2026-09-11。状态：对话需求已整理，技术方案供实现使用；尚未实现或实机验收。

关联：[详细实现计划](../plans/2026-09-11-material-planner.md)。代码核查基线：`c82e10fc`，`config.py` 为 `1.58.00`。本次仅新增文档，不改变程序版本。

## 1. 目标与范围

主要参考 StarRailCopilot（SRC）的材料字典、分组、单向合成、库存校准和按缺口选本思路，适配鸣潮实际页面。形成三个独立数据源：游戏培养目标提供需求，仓库扫描提供实际库存，每次结算提供实际收益流水。

第一阶段建立扫描、缺口判断、按需刷取和永久收益统计。均值先展示和积累，不自动替代真实库存；后续在数据质量和预测误差验收后启用均值预测，临近目标复核库存。该分阶段安排是实现建议，不将“样本数多”视为已经实证可用。

### 已确认的材料范围

| 类型 | 记录 | 自动刷取与结束条件 |
|---|---|---|
| 凝素领域武器与技能素材 | 实际库存、分品质需求、缺口、收益 | 属于十个目标材料组的才刷；自身库存及同组合成可满足时停刷 |
| 共鸣者突破材料 | 培养页持有量、需求量、缺口 | 暂不刷；不阻塞声骸阶段，待已有模块完成后接入 |
| 技能升级材料 | 即周本材料；只从培养目标页读取并展示，不要求仓库扫描 | 有指定目标按目标；未指定自动选择游戏列表第一个周本；受剩余次数、体力约束 |
| 大世界怪物材料 | 仓库及收益可记录 | 不专门花体力刷，不阻塞声骸阶段 |
| 植物等采集素材 | 培养页可记录 | 不纳入体力刷取 |
| 通用兑换材料 | 扫描可标记保存 | 不参与库存可用量、合成额度、缺口抵扣，不自动兑换 |
| 声骸培养 | 记录目标方案及可用入口 | 可执行的材料目标完成后，作为持续刷取方向，直到培养目标更换；每次运行仍遵守体力预算和停止条件 |

本功能不自行新增角色养成、武器替换、自动花费货币补齐或通用材料兑换。目标由游戏当前培养方案决定。声骸“持续”指后续运行持续投入可用体力，不代表保持脚本无限运行。

## 2. 页面与识别依据

### 2.1 培养目标页

路径：大世界 `F2 → 左侧双剑「素材获取」→ 第一项「培养目标」`，右侧滚动读取。

读取目标身份、材料图标、品质、`持有量/需求量`、周本剩余领取次数；以“声骸培养”标题分隔定量材料目标和后续声骸方向。目标页的持有量是观测值，仓库实际数量用于校准；需在真实操作中验证分子是否含任何兑换折算，不能未经验证视为权威库存。

“武器与技能素材”是通用分类标题，不能直接判定来源：凝素材料和怪物材料共享这个标题。识别具体材料后按字典类型筛选。“可补齐”包含通用材料兑换能力，必须忽略其完成含义。红色、绿色数字和感叹号/勾号也不能替代程序的缺口计算。

截图示例：一个旧角色搭配新武器，培养页存在两组凝素材料和两组怪物材料。两组凝素必须独立保存，不按角色版本合并、猜测或互相抵扣。

### 2.2 凝素列表

只使用武器类型文字：`迅刀、音感仪、长刃、臂铠、佩枪`。不依赖凝素副本名称。

五类武器各有两套材料，共十个材料组，每组绿、蓝、紫、金四档，共四十种具体材料。组 ID 使用 `sword_a/b、rectifier_a/b、broadblade_a/b、gauntlet_a/b、pistol_a/b` 这类稳定内部标识；a/b 只区分图标系列，不将未经核验的年代含义写死。

用户提供参考：列表有二十个选项，前十个为 3.0 时期，后十个为 2.0 时期。二十个入口不等于二十种材料，顺序只能辅助查找。实际选中条目必须同时满足武器类型和材料预览图标；不能仅凭列表编号或前后十项决策。多个入口匹配同一组时，优先沿用已有明确选择，首次使用可取首个通过核验的入口。

预览会横向滚动，金色图标不保证始终在某个固定位置；培养页常见绿→金、预览常见金→绿，不靠位置决定品质。带 `300` 的黑金圆形图标是经验值，不属于目标材料。

### 2.3 仓库

路径：大世界 `B → 药丸图标下方「资源」页签 → 置顶 → 滚动到底`。

格子读取图标、品质和数量；未知或歧义材料点击后 OCR 右侧正式名称和“拥有 N”复核。右侧详情保持原选中物品，滚动不保证改变详情，必须确认选择变更后才能关联名称。头像、“新”、选择边框应避开或遮罩，不进入核心模板区域。

同一材料跨屏重复出现是同一库存，不能加和。四档品质可能相隔多屏或缺失；不能假设某组连续排列。部分显示的格子不读取不完整数字。完整遍历并排除未知格子可能性后，才允许将未出现的已知材料记为零；否则记未知。周本材料不需要在此扫描，其他资源都可保留分类记录。

每账号首次运行扫描；每周一扫描一次，本周未运行则在周一之后首次运行补扫。按已有国服周界（UTC+8 周一 04:00）实现，其他服务器若支持需独立配置。只有完整扫描成功才更新周扫描标记；异常和半次扫描不覆盖完整基准。目标更换、用户手动要求、库存不可信时允许补扫。日常临近停刷仅校准相关材料组，不重复全仓库扫描。

## 3. 单向合成与缺口

实际存储始终保留四档整数：`green、blue、purple、gold`，均不得为负。同组相邻品质 3:1 向上合成，不能向下或跨组。绿色等价值：

```text
E = green + 3*blue + 9*purple + 27*gold
```

E 是统计单位，不是实际分解。停刷必须先做有方向的逐级分配：从绿开始，优先满足本档需求，记录不足；只有本档剩余的完整三份才能向下一档结转。紫到金同理。四档缺口全零才表示材料足够；这表示“材料可满足”，不保证已实际合成。第一版只计算虚拟合成，不自动操作合成界面。

```text
库存只有金1，需求绿3：E库存27 > E需求3，但仍缺绿3，不能停刷。
库存绿15、蓝6、紫0、金0；需求绿6、蓝3、紫2、金0：可满足。
```

计算返回每档缺口和虚拟合成次数；缺口等价值用于展示/预测。若逐档不足，例如蓝不足，即使金富余也不能抵扣。原始库存和需求不被虚拟计算改写。

当角色升级、武器改变、行迹提升后，旧需求不再可靠。重新读取目标并创建新需求修订，不把新库存减旧需求，也不把目标页重复扫描当成新增需求。第一版围绕当前培养目标，不新增多个独立角色同时预占共享库存的算法。

## 4. 结算采集与奖励份数

### 4.1 以一次实际领取为结算单位

战斗、领取、奖励份数、截图张数是四件不同的事。一场凝素战斗通常消耗 80 体力领取，少数为 40；同一结算可以跨多张滚动截图。必须在离开/再次挑战之前抓取完整列表。

每次领取确认前生成唯一 `claim_id` 并持久化意图；确认真实体力扣除后关联消耗量。保存全部原始帧和解析结果，捕获失败不得重复点击领取。重进同一结算继续采集沿用原 claim_id，新战斗/新领取才产生新 ID。

### 4.2 不检测活动，也不依据“双倍”乘算

只记录实际消耗体力、实际掉落和奖励份数。显示的 `×N` 是观测数量，不额外乘二。“双倍”文字不作为活动分类、领取计数或过滤条件。

用户确认：目标组绿色材料每份奖励必有一个独立格子。因此：

```text
奖励份数 = 完整结算中去重后的目标组绿色格子数
```

这是格子数，不是材料个数。必须排除其他绿色怪物材料。可能得到 1、2、4 份，也不将其他正整数一律判错；若界面合并格子或缺少绿色格子，使本规则无法确认，保存记录并标为计数未知，不从体力或“双倍”补猜。

### 4.3 滚动去重

先重建一份完整的有序掉落列表，再按材料加总。同一物品在不同列表位置是不同掉落，即使数量完全相同也要保留；跨截图同一位置只计算一次。禁止使用 `set(item_name, amount)` 或整图哈希作为结算唯一标识。

通过相邻截图的行序列、图标布局和实测垂直位移建立重叠关系，维护绝对行号和列号。若多种对齐同样成立，缩短滚动并补帧，不强行去重。置顶、到达底部且列表稳定作为完整性依据；“已看到一个绿色材料”或“两张截图”不能作为结束依据。截图均重复也不单独证明到底，需要滚动边界/底部布局证据。

### 4.4 已有样本验算

用户 17:40 两张截图是同一次领取的滚动视图，中间一行重叠。目标为音感仪的一组螺旋材料：

| 项目 | 值 |
|---|---|
| 实际体力（用户说明） | 80 |
| 绿色独立格子 | `×7`、`×6`，2 格 |
| 合计绿/蓝/紫/金 | 13 / 16 / 3 / 0 |
| 奖励份数 | 2 |
| 绿色等价值 | 13 + 16×3 + 3×9 = 88 |

80 体力不是仅从截图“剩余3”推算所得，实机必须用已有扣除确认。两张截图不能作两个统计样本。金为零只在完整列表已确认后成立。此样本用于回放验收，不能宣称已建立长期均值。

## 5. 永久数据与统计

### 数据分层

| 数据 | 必要字段 |
|---|---|
| 材料字典 | item_id、group_id、weapon_type、rarity、source_type、正式名称/别名、模板版本 |
| 培养需求修订 | profile_id、target_revision、角色/武器/目标指纹、扫描时间、按材料需求、周本行、声骸方向、完整状态 |
| 库存快照 | snapshot_id、profile_id、时间、week_id、逐材料实际数量、全量/局部、完整状态、来源帧 |
| 领取意图及结果 | claim_id、profile_id、run_id、target_revision、group_id、入口/难度指纹、创建时间、实际体力、扣除确认状态 |
| 截图 | claim_id 或 snapshot_id、frame_seq、相对路径、SHA256、尺寸、捕获时间 |
| 解析修订 | claim_id、revision、parser_version、完整状态、奖励份数、逐材料总量、异常原因 |
| 掉落条目 | claim_id、解析修订、绝对格子编号、item_id、品质、数量、来源截图与坐标 |

建议使用标准库 SQLite 加不可变 PNG，放在 `%LOCALAPPDATA%/OKWW/MaterialPlanner/`，避免工作区更新及普通截图清理。数据库 `index.sqlite3`，图片 `assets/<profile_id>/<record_id>/<frame_seq>.png`。数据库中的记录、截图和原始解析均不自动删除；纠错创建新解析修订，统计选最新有效修订，不覆盖原始证据。账号改名保留 profile_id；删除账号配置不级联删除历史。

复用现有证据库的“SQLite＋不可变原图”做法和可复用写入机制，但材料记录单独存储：现有 `EvidenceRepository.permanently_delete()` 和普通完成证据管理不能删除材料原件。不引入额外数据库服务或网络上传。明确备份使用 SQLite backup 加引用图片复制，不做轮换删除。写满磁盘或保存失败应中止下一轮领奖并显示错误，不能用删除旧数据自动恢复。

### 统计口径

仅完整识别、奖励份数可靠的结算参与每份均值；每体力统计还要求消耗体力已确认。失败、部分、未知记录永久保存，但不视作零收益。不删除离群的真实记录，不依据是否活动剔除样本。

```text
每份各品质均值 = 各品质掉落累计 / 奖励份数累计
每体力收益 = 掉落累计 / 实际消耗体力累计
每份绿色等价值 = (累计绿 + 3累计蓝 + 9累计紫 + 27累计金) / 累计奖励份数
```

不对每场均值再无权平均，不用体力/40代替观测份数。按材料组和可影响掉落的难度/版本指纹分别展示；未知难度可统计于独立桶，不能默默合入已知难度。默认按账号展示，可合并相同条件账号统计，但库存永不跨账号共用。

展示结算数、奖励份数、完整率及时间范围。平均值可能受历史奖励份数/体力关系影响，对未来体力耗费仅作估计，不保证下一次额外奖励。不需要新增活动识别模块。

## 6. 调度与现有模块接入

建议的规划顺序：验证当前账号 → 按周需要扫描仓库 → 读取/校验当前培养目标 → 周本有效目标或首项回退 → 当前凝素缺口 → 声骸方向。周本没有领取次数时显示“本周不可领”，不宣称材料已满，也不无限阻塞其他可执行任务。体力预算、备用体力策略、停止指令保持生效。

| 现有代码 | 接入职责 |
|---|---|
| `DailyTask._run_daily_inner()`、`_active_profile_id()` | 已验证账号下运行规划，隔离库存、周标记和收益 |
| `BaseWWTask.use_stamina()`、`_confirm_stamina_used()` | 保持真实扣除确认，追加单次最多领取份数限制，不能假设选择按钮就已扣费 |
| `DomainTask.farm_in_domain()` | 领取后、点再次挑战前采集完整收益；最后一次体力用尽也采集 |
| `ForgeryTask.farm_forgery()`、`teleport_into_domain()` | 按材料组核验入口、单次执行与目标切换 |
| `WeeklyBossTask.run_for_target()`、`DailyTask.check_weekly_boss()` | 复用周本战斗和次数复核；新增未指定时首项逻辑 |
| `TacetTask.farm_tacet()` | 材料阶段结束后使用已核验的声骸刷取目标 |

现有 `Weekly Boss Target='无'` 表示禁用，与“未指定目标选首项”不同。建议仅在启用养成规划时增加“自动”语义：明确禁用仍禁用；启用且未指定则取当前游戏列表首个可识别周本，不能假定静态 `WEEKLY_BOSSES[0]` 等于首项。未知/错误目标不回退首项，避免掩盖识别失败。

已有周本逻辑以剩余次数耗尽记录周任务完成；若新增“目标材料已够”提前停止，应记录为目标已满足而非本周次数已用完。第一版周本维持现有领取次数策略，不额外引入库存扫描及缺口预测停刷。

现有无音区有多个候选，第一版可使用已有用户选择并核对属于当前声骸方向；未配置时采用培养页首个已支持、可消耗体力的无音区入口。不自动把列表中的声骸首领等同于无音区；仅存在不支持入口时展示未支持并停止该分支。这是建议的确定性默认规则，需要在真实入口回放中验收。

## 7. 可靠性边界

- 部分扫描不覆盖完整库存，未知数量不归零；目标不明不花体力。
- 结算记录由 claim_id 保证幂等，截图哈希只用于证据完整性；不同领取即使掉落一样也算不同记录。
- 收益统计不直接累加到权威库存。可以维护明确标记的估计库存，但不得把它写回实际库存快照。
- 奖励完整性和体力确认分别记录，某项失败不伪造另一项；采集失败不重领已消耗奖励。
- 关闭、停止、崩溃恢复检查未完成意图，只补采集/复核，不自动再次确认支付。
- 停止、死亡恢复、账号切换后清除当前规划运行上下文，永久数据仍保留。
- 使用本地虚拟环境测试；不为本功能重写登录、账号切换或战斗。
