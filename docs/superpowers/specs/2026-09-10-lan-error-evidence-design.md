# 局域网日志与错误前后截图自动同步设计

日期：2026-09-10。主体实现版本：1.54.00。本文为设计基线；本机自动化验证与异机真实验收应分别记录，不能相互替代。

用户最新分工：当前电脑完成主程序开发、测试并发布 GitHub；另一台电脑更新后只执行配置、实机验收与问题回传。原文将开发交给发送端 AI 的安排已撤销。

用户已确认：两台电脑在同一局域网；日志自动发送；错误前 10 秒、后 5 秒，每秒采样 1 张游戏截图。本文件中的资源限制和时延指标为建议实现基线，需通过实测验收。

## 1. 目标与设备角色

- 接收端 R：用户当前电脑。提供 Windows SMB 共享目录，接收日志、截图和事件索引，供本机 AI 分析。
- 发送端 S：另一台运行 ok-wuthering-waves 的电脑。自动采集、缓存、封装、上传和断线补传。
- 仅同步程序诊断数据与游戏画面；不扩展为整个桌面监控、远程控制、持续录像或自动修改游戏行为。
- 当前电脑交付程序实现、发布版本和异机操作文档；具体共享地址与凭据使用本机设置，不固化进全局代码。

当前默认目标是一个已有 NAS 路径，不应假定它就是当前接收电脑。通过本机设置修改目标，不把某台电脑的 IP 写进全局默认值。

关键缺口：

1. 通用 ERROR 目前节流抓取单张最近帧，没有全局前 10 秒、后 5 秒事件窗口。
2. frame_provider 读取 executor._frame，它可能是缓存旧帧；读取时间不等于实际捕获时间。
3. 本地 worker 当前使用队列空闲超时 30 秒触发周期批次。要满足快速持续日志同步，应改成独立单调时钟截止时间，不能只把空闲超时改短。
4. 现有批次按日志与截图分目录；需要新增跨批次的事件关联，不能假定同目录即同错误。
5. 现有 PNG 重编码没有对画面文字进行自动打码。不能把 reviewed_image 参数理解为已自动脱敏或已有人逐张检查。

## 3. 方案选择

| 方案 | 优点 | 代价 | 决策 |
| --- | --- | --- | --- |
| 复用 SMB 上传 | 已有凭据、补传、校验、状态界面，当前电脑仅需共享文件夹 | 需配置共享与 NTFS 权限 | 推荐 |
| 新建 HTTP 接收服务 | 可独立定义接口 | 新服务、鉴权、部署、端口与重试维护 | 本期不采用 |
| 通用文件同步软件 | 容易同步已有文件 | 无法单独解决错误前帧缓存、日志关联和提交完成判定 | 不作为主方案 |

数据流：游戏帧 → 有界帧缓存 → 错误事件冻结/后续采样 → 本地持久化 → 既有批次封装 → SMB → 校验完成 → 接收端证据索引。

日志单独持续走增量上传，不等错误，也不等后 5 秒截图完成。

## 4. 采样与触发契约

### 4.1 时间定义

以触发时刻 t0 的 monotonic 时间划窗；墙钟使用带时区 ISO 8601，仅供显示和跨设备排查。系统校时不能改变窗口长度。

- 前窗口：[t0−10s, t0)，从已有采样中选择，最多 10 张。
- 当时帧：触发后尽快读取 1 张可用的最新帧；记录实际时间差，不伪称恰好 t0。
- 后窗口：(t0, t0+5s]，目标 t0+1、+2、+3、+4、+5 秒各 1 张。
- 健康稳定单事件最多约 16 张。启动不足 10 秒、调度延迟、帧源不可用时允许少于此数，但必须记录缺失原因。
- 环形缓冲可短暂保留 12 条以容忍边界，真正选帧仍按时间窗口截断。
- 正常运行只保留滚动缓存；未触发的帧过期释放，不持续上传。

### 4.2 触发条件

全局 logging.ERROR/CRITICAL、sys.excepthook 和 threading.excepthook 触发。WARNING、普通截图保存、正常退出不创建新的错误事件。

不要通过对所有日志搜索“失败”二字替代结构化触发。仅存在于外部日志文件、未经过当前进程日志/异常钩子的错误，继续同步日志，但本期不保证相应前后截图。

异常钩子和日志系统可能报告同一次异常，应按异常关联信息在短时间内去重；无法确定同一异常时保留触发记录，由事件合并限制重复图片。

### 4.3 连续错误

同一进程只维护一个活动截图窗口。在活动窗口内的新错误追加 trigger 记录，共享已有图片，并延长采样到最新错误后 5 秒。

为避免错误风暴永不封口，每个事件自首次触发起最多持续 30 秒；到边界原子封口，后续仍有错误则创建关联的下一事件，carry-over 说明上一事件后窗口未完成的原因。采样缓存继续运行，使新事件仍有前帧。

不是按 logger 去重后丢弃错误文本。触发记录、错误数量、截图降采样和截断原因都要可见。

## 5. 帧源与并发

- 优先复用框架现有游戏捕获结果；先确认读帧线程安全性及捕获时间/帧序号是否可取得。
- 将“读取时刻”和“源帧时刻”分字段记录。源帧时间不可获得时填写 null，freshness=unknown，不用读取时刻冒充。
- 判断帧是否更新优先使用真实捕获序号/时间。图像摘要相同可能只是静止场景，不能单凭相同像素宣告冻结。
- 任务因错误停止后，仍需验证捕获是否继续刷新。若框架仅随任务获取新帧，应利用现有捕获器提供的安全接口补充后窗口采样；不得并发调用不支持并发的捕获器。
- 无安全获取新帧方法时，将后窗口标为 incomplete，提供 stale_frame/frame_unavailable 等原因，不能重复旧帧凑数量。
- 截图操作不激活窗口、不发送按键、不改变战斗或账号切换状态。
- 日志回调只记录轻量触发信息，不做网络、PNG 编码、目录递归或等待后 5 秒。
- 采样与本地封装各有清晰线程所有权；上传保持独立进程。异步消费前安全复制帧，避免框架覆盖共享数组。
- 新增诊断内部异常写受控本地状态，避免递归触发新的截图事件。

## 6. 本地数据与协议兼容

### 6.1 本地事件模型

在单次诊断 run 下增加 events/<incident_id>/，存储事件元数据与本次冻结图片；与原 events.jsonl 日志文件区分。

事件索引至少包含：

| 字段 | 含义 |
| --- | --- |
| schema_version | 事件模式版本，初始 1；独立于现有批次协议版本 |
| incident_id、revision | UUID 与不可变快照序号 |
| device_id、installation_id、run_id、version | 设备、安装实例、运行批次和程序版本 |
| state | collecting / complete / incomplete |
| triggered_at、trigger_monotonic | 带时区显示时间与划窗基准 |
| pre_seconds、post_seconds、sample_interval | 本次采集参数 |
| triggers | 错误时间、来源、级别、异常类型和脱敏摘要 |
| frames | frame_id、相对时间、读取/捕获时间、freshness、尺寸、SHA-256、阶段 |
| frame_refs | 实际上传 batch_id 与 manifest 内相对图片路径；待封装时可空 |
| missing_frames、incomplete_reasons | 缺失槽位、原因，不把部分数据标成完整 |
| log_refs | run_id、日志来源与偏移/事件序号、相关批次引用 |
| continued_from / continued_to | 错误风暴分段关联 |

正常流程：rolling → collecting → complete → 本地批次 ready → uploading → uploaded。采集状态和传输状态分开：截图 incomplete 也可以上传成功。

### 6.2 持久化和两阶段发送

触发后立即将前帧与当时帧交给本地 worker 保存，生成 revision 1（collecting）并封装上传。后帧可逐步落盘；窗口结束后生成下一份不可变快照，列明最终图片引用。

已标记 _READY 的批次永远不改写。后续快照进入新批次，接收端根据 incident_id 和 revision 汇合，不能靠覆盖旧远端 JSON 更新状态。

事件 JSON 必须显式纳入封装，不能假定现有 log_sources 会递归发现 events 目录。同样，图片必须进入现有 sanitize_file、摘要与 manifest 路径，不直接复制到远端绕过验证。

### 6.3 复用现有远端结构

```text
<接收共享目录>/
  待分析/
    日志/okww-custom/<date>/<run_id>/<batch_id>/...
    截图/okww-custom/<date>/<run_id>/<batch_id>/...
  已处理/<date>/<run_id>/<batch_id>/evidence-index.json
  错误/...
```

保留 manifest schema_version=1、_READY、_UPLOAD_COMPLETE、摘要校验和现有目录深度。设备身份从 metadata 和事件索引读取，暂不插入新的设备目录层，避免破坏 control_directory、reader 与 retention。

新增事件聚合索引建议写入独立的 事件索引/<device_id>/<run_id>/<incident_id>.json；它是可重建视图，不能作为上传成功依据。路径标识必须经过白名单或现有安全路径校验。

接收端只接受完成且校验通过的批次。最新事件修订到达但引用图片未到齐时，显示 waiting_for_frames，后续扫描重新聚合；不能只凭最新 revision 就宣告事件完整。

## 7. 时延、补传与容量

正常 LAN、发送接收均在线、无积压时的验收目标：

| 项目 | 目标 |
| --- | --- |
| 新增日志本地封装 | 每 2 秒检查，按独立截止时间执行 |
| 普通日志远端可验证 | 95% 在写入后 10 秒内 |
| 前帧与当时帧远端可验证 | 95% 在错误后 10 秒内 |
| 最后后帧与最终索引可验证 | 95% 在最后一帧采到后 10 秒内，即通常 t0+15 秒内 |

上传唤醒存在 5 秒节流、任务存在约 1 分钟兜底周期，单轮上传也有时间预算。实施必须测量整条链路，并保证活跃发送端在 worker 结束后仍会处理待传数据，不能只把日志超时改为 2 秒就声称满足指标。

保留现有重试退避 5/15/60/300/900 秒。长期断网恢复后，普通情况下可能要等下一次到期重试，最长约 15 分钟加调度间隔；“重试上传”可提前触发。该恢复时延不同于在线实时同步目标。

后台任务目前依赖当前用户登录。用户注销、发送端关机、系统休眠期间不会持续采集或保证后台补传；再次登录运行后恢复。接收端关机时积压在发送端。

建议资源基线：

- 采样目标保持游戏原始分辨率，支持至 3840×2160；超出时等比例缩至此范围，并记录原始/输出尺寸。
- 缓存优先使用后台压缩后的 PNG，环形缓存压缩字节上限 128 MiB；编码中原始副本最多 2 份，全部新增采集内存预算 256 MiB。
- 单图片编码后上限 16 MiB，单事件累计图片上限 128 MiB，达到上限停止新增图片并记录容量原因；日志继续上传。
- 错误风暴事件最多约 41 张（前 10、当时 1、持续后段 30），仍受字节上限约束。
- 队列满时优先保留已冻结错误证据，丢弃未触发滚动候选，记录 dropped_frames，不能无声丢失或无限扩容。
- 本地待传达到 2 GiB 或磁盘剩余不足 2 GiB 时，暂停新增诊断图片并显示告警；允许参数调整。保留既有待传材料，不自动删除未上传证据。日志只能尽力写入，磁盘耗尽时不能承诺绝不丢失。
- 不把本次功能包装成对断电零丢失的保证；内存前帧在首次持久化前可能丢失。

## 8. 保留策略与隐私

延续当前每周清理已上传超过 7 天日志的策略；待传资料不自动删除，截图不因该规则被删。新的错误截图目录不得误用账号切换专用的 20 事件/500 MiB 清理规则。

事件索引中的异常摘要、堆栈与日志片段属于日志，应随相应日志清理而移除；接收端聚合视图也必须清除这些副本。可保留不含日志内容的图片关联、时间、完整性与 log_retention_expired 标记，不能让索引看起来仍有可读取的原日志。

共享仅面向可信 LAN 和指定账号。密码由用户在发送端界面或系统凭据界面填写，不进入需求文档、源码、聊天记录或测试输出。共享权限与 NTFS 权限都需要满足读写、重命名、校验及现有日志清理所需的目标范围内删除权限。

文本继续使用现有脱敏；游戏截图可能包含昵称、UID、聊天内容等，PNG 重编码只处理格式/元数据，不保证遮挡这些内容。本期按用户授权同步游戏截图，不额外引入逐张人工审批或声称已自动打码。

## 9. 接收端部署

1. 确认当前电脑的 LAN 地址和稳定主机名；建议 DHCP 保留地址。不能把代码中既有 NAS IP 当作当前电脑地址。
2. 用户选定专用接收目录，例如 D:\OKWW-Diagnostics；示例不是已存在路径。
3. 建立专用共享，例如 OKWW-Diagnostics，形成 \\<接收端地址>\OKWW-Diagnostics。
4. 设置专用账号与最小必要目录权限。防火墙允许专用网络上的 SMB（TCP 445），范围限制为发送端或本地子网；不关闭防火墙或开启访客匿名共享。
5. 发送端“工具 → 日志与诊断”配置上述路径及凭据，保存后进行独立测试目录的写入、读取、改名、删除验证。
6. 接收端运行现有 diagnostic_reader 可生成验证索引；错误事件聚合能力需要实施后才可使用。接收目录本身不要求安装 Python。

本期不强制新建 Windows 服务、HTTP 服务或通知平台。若后续要求接收端自动扫描，可在本机登录会话下增加明确归属的定时扫描任务，幂等运行，不执行收到文件中的任何指令。

## 10. 实施分工与涉及文件

当前电脑 AI 负责扩展采集、关联、上传调度、状态和测试，并统一发布 GitHub 版本。发送端 AI 只更新实际运行程序、配置本机上传目标、执行实机验证并回传问题；不修改源码、不重新发版。接收端负责共享目录、权限、数据验证和双机配合。

实现补充：执行器在自己的线程刷新带捕获时间的 `_diagnostic_frame`，等待/暂停时约每 0.8 秒补采；诊断 worker 按每秒采样并压缩，不并发调用捕获器。结构化图片摘要和生成的协议标识按格式验证后保留，避免被手机号脱敏规则误改；错误消息仍脱敏。界面提供“测试共享连接”和“测试错误截图”，异机无需通过改代码触发测试。

建议最小新增模块为 src/runtime/diagnostic_evidence.py（采样窗口与事件状态），接入 session、lifecycle。根据实际需要调整 collector/export、uploader/reader/retention、DiagnosticStatusCard；不全盘重写传输。

新增模块如被独立运行环境导入，必须确认 diagnostic_runtime 的文件收集和依赖复制包含它。测试最低覆盖现有 TestDiagnosticPipeline、TestDiagnosticPolicy、TestDiagnosticStatusCard，并增加有界窗口测试。Python 使用仓库本地 .venv。

实现时遵循实际 AGENTS.md；代码变更须同步版本与发布说明，按当前用户规则完成验证、提交、对应注释标签和推送。本设计文件本身不触发产品版本升级。

## 11. 验收矩阵

| 场景 | 必须可验证的结果 |
| --- | --- |
| 正常运行至少 20 秒后触发单个 ERROR | 前 10 秒、当时、后 5 秒的实际时间与图片关联正确；健康采样目标 16 张 |
| 启动 3 秒即报错 | 仅保存已有前帧，明确 warmup，不生成假的历史画面 |
| 任务错误后停止 | 验证后 5 秒获取的是新帧；不可得时明确 incomplete |
| ERROR、主线程异常、线程异常 | 都能进入统一路径；同一异常不无意义重复上传图片 |
| WARNING、正常退出 | 不创建新错误窗口；既有普通截图同步仍工作 |
| 持续 ERROR 60 秒 | 事件按 30 秒上限分段，日志不断，内存与队列有界 |
| 冻结帧/无帧/最小化 | 正确标记 freshness 和缺失原因，不拿旧帧凑数 |
| 强制终止/正常退出发生在后窗口中 | 已落盘图片可恢复补传，事件标为不完整，不承诺未来画面 |
| 接收端离线后恢复 | 本地积压、重试、重启后补传；完整性摘要一致 |
| 上传中断、重复上传、批次乱序 | 不读取半包、不重复完成、最终索引等图片到齐 |
| 日志持续写入且截图队列繁忙 | 周期日志不会被队列空闲超时饥饿，在线时延达标 |
| 两台发送端/两安装实例 | 身份可区分，运行与事件不串联，后台任务互不抢占 |
| 日志轮转、策略前历史 | 既有增量采集不回归，不默认上传全部历史 |
| 7 天已传日志清理 | 图片保留、日志及索引副本按规则清理、引用显示过期 |
| 错误密码、1219、磁盘不足、畸形图片 | 不阻塞游戏、不断开无关 SMB 会话、有可读状态 |

时间窗口、状态、故障和资源限制先用假时钟与带编号图片进行确定性测试；实际双机至少 20 个低频受控事件，报告分位时延、接收目录、版本、截图序列和待传状态。实机结果未完成前不得写“全部验收通过”。

## 12. 发布、回退与交付

交付代码差异、测试命令与结果、实机证据、配置方式、版本与提交标识、已知限制。回退时先停止新增截图采样，保留日志同步及已有待传批次；不通过删除诊断目录解决异常。事件格式是附加协议，旧批次仍应可上传、验证和清理。

后续是否增加自动截图打码、视频、跨网络传输、自动根因分析与通知，独立提出，不包含在本期承诺内。
