# 账号总配置与完整性保护设计

日期：2026-08-18  
状态：待用户审核  
目标版本：1.06.00

## 1. 背景

当前账号方案、账号别名、账号序列和任务完成记录共同存放在
`working/configs/daily_profiles.json`。账号切换时，程序还会把当前内存中的
`DailyTask` 配置写回旧方案。只要“当前方案标签”和内存中的实际配置发生错位，
就可能把一个账号的任务配置保存到另一个账号名下。

现有写入还存在以下风险：

- 方案应用是逐字段持久化，异常退出可能留下半旧半新的配置；
- 完成记录依赖当前显示的方案名称，名称错位时可能写入错误账号；
- 多账号任务为了临时关闭单账号退登，会修改持久配置并在 `finally` 中恢复，
  进程被强制终止时可能无法恢复；
- 普通 JSON 保存不是原子替换，异常终止时可能产生截断文件；
- 只把 UI 控件禁用，不能阻止后台代码继续写入账号配置。

因此，本设计增加一份主程序只读的总配置，将它作为账号任务意图的唯一可信来源；
保留现有配置作为兼容工作副本，同时通过启动门禁、运行前复检、事件留证和人工恢复
阻止异常配置进入自动任务。

## 2. 目标

1. 程序正常运行期间永不写入账号总配置。
2. 总配置记录所有账号“做什么、按什么顺序做、计划何时做”等稳定意图。
3. 上次完成时间、当前游标和断点等运行状态与稳定意图彻底分离。
4. 保留现有用户配置文件，降低升级和旧界面的兼容成本。
5. 每次启动、每次多账号任务开始前和每次账号切换前检查配置完整性。
6. 检测到差异时先留存完整证据，再阻止自动任务；必须由用户明确处理。
7. 恢复操作必须备份、校验、原子替换，失败时保持安全模式。
8. 通过版本化结构和扩展命名空间，为以后增加用户配置留出兼容空间。

## 3. 非目标

- 不依靠 Windows“只读”属性作为唯一保护。程序与用户使用同一 Windows 身份时，
  文件系统不能可靠区分用户手工修改和程序错误写入。
- 不阻止用户或其他具有相同权限的进程主动修改文件。
- 不在本次设计中制作完整的配置编辑器。用户通过文件夹中的 JSON 修改总配置。
- 不允许在发现未解决差异后“忽略并继续执行自动任务”。
- 不把 GitHub 日志传输作为本模块的运行依赖；事件目录可以由后续诊断上传功能采集。

## 4. 方案选择

### 4.1 采用：只读总配置 + 兼容工作副本 + 独立运行状态

总配置是唯一可信来源；现有配置继续存在，但只能作为 UI 展示和旧逻辑兼容的工作
副本。自动任务只使用已经校验通过的总配置内存快照。两者不一致时进入完整性门禁。

优点：既切断错误写回的污染路径，又不必一次删除所有旧配置和旧界面。  
代价：需要迁移、比较、门禁、恢复和状态拆分，属于中等架构变更。

### 4.2 未采用：删除现有配置，所有任务直接读取总配置

这是结构最简单、长期最干净的方案，但会立即破坏现有 UI、迁移逻辑和其他任务对
`DailyTask.json`、`daily_profiles.json` 的依赖，升级风险过高。

### 4.3 未采用：保留 UI 编辑，只增加锁、事务和哈希

可以降低文件损坏概率，但程序仍然拥有修改账号方案的正常入口。一旦账号身份、当前
标签或提交对象选择错误，事务只会更可靠地提交错误数据，无法根治跨账号污染。

## 5. 文件与字段所有权

### 5.1 `working/configs/account_master_config.json`

账号稳定意图的唯一可信来源。主程序只读取，不提供保存、修复、自动迁移或自动补全
接口。初始文件以及后续修改由用户或运行端 AI 在主程序之外完成。

初始结构如下；具体任务字段沿用当前 `DailyTask.PROFILE_KEYS` 的合法值：

```json
{
  "schema_version": 1,
  "config_id": "primary-account-plan",
  "timezone": "Asia/Shanghai",
  "profiles": {
    "0f7b7f52-9da7-4b43-bbc2-9be7c539f801": {
      "display_name": "A1",
      "account_aliases": ["A1", "199****0001"],
      "task_config": {},
      "schedule": {},
      "extensions": {}
    }
  },
  "sequences": {
    "序列一": ["0f7b7f52-9da7-4b43-bbc2-9be7c539f801"]
  },
  "extensions": {}
}
```

字段规则：

- `schema_version`：结构版本。高于程序支持版本时必须进入安全模式，禁止猜测解析；
- `config_id`：区分多套总配置，参与事件记录；
- `profiles`：以不可变 `profile_id` 为键，显示名和别名变化不影响状态归属；
- `task_config`：账号要执行的任务及稳定选项；
- `schedule`：计划运行条件。实际完成时间不放在这里；
- `sequences`：只引用 `profile_id`，禁止使用易变的显示名作为外键；
- `extensions`：保留未知、带命名空间的未来字段。主程序只验证结构，不写回或删除。

`schedule` 在结构版本 1 中是受保护的声明性记录，使用 `mode`、`local_time`、
`weekdays` 和 `extensions` 表达用户计划。目标版本只负责验证、比较和只读展示，不据此
创建、删除或修改 Windows 计划任务，也不在运行中自动跳过账号。以后如果由总配置接管
Windows 计划任务或账号执行窗口，必须提升 `schema_version` 并单独设计迁移，不能静默
改变结构版本 1 的行为。

程序对该路径的所有通用 JSON 写入调用都必须显式拒绝。项目测试还要扫描主程序的
写入入口，防止未来重新引入保存接口。Windows 文件只读属性可以作为附加提示，但
不能替代代码级边界。

### 5.2 `working/configs/daily_profiles.json`

保留为兼容工作副本。它继续向旧 UI 提供展示数据，但以下字段由总配置保护：

- 账号稳定 ID、显示名和账号别名；
- 账号专属任务配置；
- 账号归属序列；
- 计划执行条件。

受保护字段只能在用户批准“按照总配置修复”时被完整性恢复服务写入。账号切换、
对话框关闭、任务完成和普通配置保存都不得回写这些字段。账号配置 UI 改为只读展示。

### 5.3 `working/configs/account_runtime_state.json`

仅保存程序运行产生的数据：

- 各 `profile_id` 的任务完成时间；
- 当前序列、当前游标和已完成账号集合；
- 可恢复的任务断点；
- 最近一次验证通过的总配置指纹；
- 最近一次完整性事件和用户处理结果的引用。

该文件允许程序写入，但必须使用进程内锁和“临时文件、刷新、校验、原子替换”流程。
所有完成记录 API 必须显式接收 `profile_id`，不得从当前 UI 标签推断账号。

### 5.4 `DailyTask.json` 和其他普通配置

只保留全局选项、非账号专属选项和 UI 状态。多账号任务对“单账号任务完成后是否
退登”等选项的临时覆盖只存在于内存，不能再修改持久配置后依赖 `finally` 恢复。

## 6. 规范化比较

完整性检查比较语义，不比较 JSON 原始字节：

1. 分别读取总配置和工作副本，保留原始文件用于留证；
2. 验证 JSON、结构版本、类型、必填字段、稳定 ID 唯一性、别名冲突和序列引用；
3. 按统一的受保护字段定义转换成规范化结构；
4. 补齐程序定义的默认值、规范布尔值和枚举值，并稳定排序对象键；
5. 对规范化结构做逐字段比较并计算 SHA-256；
6. 缩进、键顺序和无关运行字段变化不算异常；
7. 账号新增、删除、改名、别名变化、任务变化、计划变化和序列变化均报告为差异。

除“总配置与工作副本”比较外，还要把总配置规范化指纹与
`account_runtime_state.json` 中上次由用户确认的指纹比较。首次部署、总配置合法修改，
以及总配置和工作副本被同时改成相同内容时，都会触发“总配置版本已变化”门禁。用户
必须确认该变化确实来自自己，程序才把新指纹写入运行状态。该确认只接受新的只读来源，
不会修改总配置；如果工作副本仍不一致，还必须继续完成恢复或手工处理。

“受保护字段集合”只能有一个代码定义，比较、恢复、UI 只读和测试都引用同一份定义，
避免各模块规则漂移。

## 7. 启动门禁与运行期复检

### 7.1 启动顺序

1. 初始化最小日志和只读配置服务；
2. 在创建任何自动任务线程、热键监听或游戏窗口前台循环之前执行完整性检查；
3. 检查通过后冻结一份不可变内存快照；
4. UI 和自动任务都从该快照读取账号稳定意图；
5. 完成门禁后才允许加载并运行正常任务。

### 7.2 运行期检查点

为防止软件启动后才发生污染，还必须在以下位置快速复检规范化指纹：

- 开始多账号每日任务前；
- 每次准备切换账号前；
- 从安全停止或暂停恢复前。

指纹变化时不得继续当前动作。任务先执行可中断的安全停止，再生成或复用完整性事件，
禁止继续抢占游戏窗口前台。

## 8. 异常事件与证据目录

异常目录格式：

`working/config_integrity_incidents/<时间>_<事件ID>_PENDING_REVIEW/`

目录至少包含：

- `manifest.json`：事件 ID、状态、时间、程序版本、总配置 ID、文件哈希和处理结果；
- `master.snapshot.json`：检测时的总配置原始快照；
- `working.snapshot.json`：检测时的工作副本原始快照；
- `normalized_diff.json`：按账号和字段组织的结构化差异；
- `integrity.log`：验证阶段、错误、调用位置和用户选择；
- `PENDING_REVIEW`：醒目的空标记文件。

事件目录不得保存 GitHub PAT、密码、鉴权 URL 或其他凭据。上传诊断包时必须再对手机号、
本机路径和其他身份信息做脱敏；本地原始快照仅用于恢复和分析。

同一组规范化差异在多次启动中重复出现时，使用差异指纹找到已有未处理事件并追加发生
时间，不重复创建大量目录。处理完成后原目录保留，原子更新 `manifest.json`，移除
`PENDING_REVIEW` 并增加 `RESOLVED_BY_MASTER_RESTORE` 或 `RESOLVED_MANUALLY` 标记。

## 9. 用户交互与安全模式

发现异常时显示阻断对话框，明确列出受影响的账号和字段，但不直接显示完整敏感身份。

交互顺序：

1. 用户点击“已知晓并查看差异”；
2. 程序展示只读差异摘要和事件目录位置；
3. 如果总配置指纹发生变化，用户先选择“确认这是我的总配置修改”或退出处理；
4. 工作副本存在差异时，用户选择“按照总配置修复工作配置（推荐）”或“退出并手工处理”。

“已知晓”只解除对诊断 UI 的阻挡，不解除自动任务门禁。选择手工处理或关闭对话框时，
程序保持安全模式：允许查看差异、打开事件目录、导出日志、重新检查或退出，但禁止启动
自动任务。正常模式只能在配置重新验证完全一致后启用。

如果用户希望以当前工作配置为新标准，程序不能提供“设为总配置”按钮。用户必须退出，
在文件夹中手工修改总配置，再重新打开或点击重新检查。

## 10. 恢复事务

当总配置有效且用户批准恢复时：

1. 获取配置恢复锁，阻止其他配置写入；
2. 把涉及的完整配置文件复制到事件目录的 `before_restore/`；
3. 从总配置构造受保护字段，保留工作副本中的非受保护兼容字段；
4. 写入同目录临时文件并刷新到磁盘；
5. 重新读取临时文件并完成结构与语义校验；
6. 使用原子替换写入正式文件；
7. 重新执行完整性比较；
8. 完全一致后记录用户选择、关闭事件并退出安全模式。

任一步失败都保留原正式文件和事件证据，不得进入正常模式。恢复不能覆盖
`account_runtime_state.json` 中的完成记录和游标。

## 11. 错误处理

- 总配置缺失：进入安全模式，提供模板和文件位置，不根据工作副本自动创建正式总配置；
- 总配置 JSON 损坏或字段非法：进入安全模式，不提供覆盖工作副本操作；
- 总配置版本过新：报告所需最低程序版本，禁止降级解释；
- 工作副本缺失或损坏：总配置有效时允许用户批准重建，原文件先进入事件目录；
- 状态文件损坏：备份损坏状态并进入安全模式；只有用户明确批准后才能创建空状态，
  同时警告可能导致当天账号任务重复执行；
- 恢复过程中进程退出：原子替换保证正式文件是完整旧版或完整新版；下次启动重新检查；
- 运行期检查失败：先停止自动操作和窗口抢占，再显示事件，不让异常处理阻塞停止按钮。

## 12. 升级与迁移

升级到目标版本前，先完整备份 `working/configs`。因为主程序禁止创建或写入正式总配置，
首次升级采用以下流程：

1. 仓库提供总配置模板、只读验证命令和运行端 AI 操作文档；
2. 用户或运行端 AI 根据现有 `daily_profiles.json` 生成候选总配置；
3. 验证工具只读取候选文件并输出问题，不修改正式配置；
4. 用户确认后在主程序外把候选文件放到规定路径；
5. 首次启动执行完整性比较，发现差异时由用户批准把总配置同步到工作副本；
6. 原 `daily_profiles.json` 始终保留，迁移不删除用户原始数据。

未来 `schema_version` 升级也使用显式、主程序外的迁移工具。主程序可以在内存中读取旧版，
但不能把迁移结果写回总配置。

## 13. 与账号切换逻辑的约束

- `MultiAccountDailyTask` 和 `TestAccountSwitchTask` 使用同一个只读快照与账号解析服务；
- 连续切换测试默认顺序保持 A1、A3、A4，但内部先解析为稳定 `profile_id`；
- 登录备用名、短名和掩码手机号都属于总配置中的账号别名；
- 账号切换不再触发“保存旧方案”或任何账号配置回写；
- 登录后必须验证实际账号与目标稳定 ID 匹配；不匹配时重新选择目标账号，而不是停止；
- 测试入口继续复用生产选择、验证、重试、退登和登录方法，不能维护独立实现。

## 14. 测试策略

### 14.1 单元测试

- 总配置有效、缺失、损坏、版本过新和未知扩展字段；
- 稳定 ID、显示名、备用名、掩码手机号和别名冲突；
- JSON 格式变化不产生差异，受保护字段变化准确产生差异；
- 运行状态和 UI 字段变化不产生差异；
- 通用写入工具拒绝总配置路径；
- 状态文件和恢复操作使用原子替换；
- 同一差异事件去重，事件状态和标记正确更新。

### 14.2 集成测试

- 配置一致时正常启动且不写任何账号方案文件；
- 差异发生在任务线程启动之前时，任务和窗口抢占均未启动；
- 点击“已知晓”后仍不能运行自动任务；
- 批准恢复时先备份、只修复受保护字段、保留运行状态并复检成功；
- 拒绝恢复时保持安全模式；
- 恢复中断后下一次启动能够重新检测；
- 软件运行中修改受保护字段，在下一检查点安全停止并留证；
- 强制停止不会把临时运行选项持久化；
- A1、A3、A4 连续切换覆盖短名、备用名和掩码手机号，且总配置与工作副本均未变化。

所有测试使用临时目录和独立配置夹具，不读取或修改用户真实配置。

## 15. 发布与验收

该设计属于中等变更，代码实施版本为 `1.06.00`。设计文档本身不修改程序代码，
因此在实施前不单独调整版本号。

发布验收条件：

1. 新增及相关回归测试全部通过；
2. A1、A3、A4 连续账号切换测试使用生产路径并通过；
3. 启动差异、运行期差异、恢复成功、恢复失败和停止行为均有测试证据；
4. 总配置在所有自动任务和测试结束后字节及语义均未变化；
5. Sol 检查 Luna 的差异、测试结果和本设计符合性；
6. `config.py`、产品版本文本和发布说明统一更新为 `1.06.00`；
7. 提交代码、创建带注释标签 `v1.06.00`，并推送分支和标签到 GitHub。
