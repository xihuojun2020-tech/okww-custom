# 多账号每周乐园与序列联动实施计划

状态：已按用户授权由 GPT-6 Sol 监督 GPT-6 Luna 实施并完成离线验收；结果见 `docs/reviews/2026-09-29-weekly-garden-implementation.md`。远端实机登录与游戏积分页面仍需使用端验证。

目标：新增由账号序列驱动的多账号每周乐园，三个执行入口共享每周乐园完成结果，同时修复当前执行账号下拉框混入其他序列账号的问题。

基线：`E:\AI work\okww-nas-20260923-recovery`，已发布 1.87.03。实现时先复核当前分支、最新版本、未提交修改与远端状态，保留已有证据及其他工作。

## 一、用户操作与确定行为

### 任务入口

新增“多账号每周乐园”，放在现有“每周任务”分类。支持现有任务启动、停止和调度入口；由用户选择空余时段运行，不自动创建外部定时任务。

卡片主配置：

| 项目 | 行为 |
| --- | --- |
| 当前序列 | 使用已有序列库；不创建第二份序列 |
| 当前序列账号 | 只读显示当前成员、顺序、乐园执行安排和本周状态 |
| 当前执行账号 | 空项＋当前序列成员；按序列顺序显示，用于声明实际已登录账号和确定起点 |
| 本次最多处理账号数 | 0 表示不限制；正整数用于分批；已完成/关闭的跳过项不占名额，一个实际进入任务的账号算一次，失败也计入 |
| 本次时间预算（分钟） | 0 表示不限制；达到预算后不再启动下一个账号，当前账号结束并保存状态后停止，可能超过预算 |
| 本周进度 | 已完成、待执行、失败待补跑、已关闭；显示数目及账号状态 |

本版在账号边界执行时间预算，不强制中断乐园对局。用户主动暂停按现有停止机制立即响应；若尚未核实积分达标，不写已完成。

两个多账号任务各自记住所选序列和起点。它们共享序列内容和筛选逻辑，但用户在一个任务中改变当前序列，不强制改另一个任务的选择。

### 乐园执行安排

账号设置新增“乐园执行安排”：`随每日执行`、`跟随多账号每周乐园`、`关闭`。保留已有“乐园检查日”，仅在用户之后明确选择随每日执行时生效。

用户确认的升级默认：所有旧账号中，原乐园检查日选择了周一至周日的，统一迁移为“跟随多账号每周乐园”；原来选择“无”的继续关闭。迁移覆盖全部账号配置，不局限于当前序列。迁移后，原已启用账号的单账号每日、多账号每日均不再按旧检查日自动运行乐园。

- 随每日执行：每日到检查日及其后按已有补检逻辑执行。用户明确启动多账号每周乐园时，也可提前处理这类账号；共享完成记录保证随后每日跳过。
- 跟随多账号每周乐园：每日不自动运行乐园；独立任务按所选序列处理该账号。
- 关闭：所有自动入口跳过，该账号状态仍可展示。

因此，独立任务的执行候选是当前序列中“乐园未关闭且本周未完成”的账号；不能用每日任务是否完成作为筛选条件。

### 序列切换规则

- 选择序列二后，当前执行账号只保留序列二成员，含空选项。
- 原选择也属于新序列时保留，否则同时清空持久配置与控件选择，不自动选第一个账号。
- 空选项沿用生产流程：运行时识别实际登录身份，再决定是否先退登/切换；不得把空项解释成已经登录首个账号。
- 空序列仅显示空选项，并提示“该序列暂无账号”；禁止回退到全部账号。
- 当前账号已完成乐园时直接跳过乐园，按生产顺序寻找其后可执行项。起点仅改变遍历顺序，正常全量运行仍覆盖当前序列所有待处理成员。
- 顺序严格来自序列，不按账号字母排序；无效/已删除成员剔除，共享成员只出现一次。
- 改名按稳定 profile_id 保持身份，不因显示名称变化丢失本周完成状态。下拉框值仍适配现有 Config/AccountChoice 约定，显示标签不充当身份主键。
- 运行期间锁定序列和起点相关编辑，使用已验证运行快照；账号身份被删除或配置完整性失效时按生产保护停止，不能运行中偷偷换一组目标。运行结束后刷新控件。

## 二、已确认的代码问题与复用边界

1. `MultiAccountDailyTask.__init__` 和 `refresh_account_options` 把所有 `profile_names` 放进 CURRENT_ACCOUNT 下拉框，因此选择序列二仍能看到序列一成员。
2. `validate_config` 已安排序列改变后的异步刷新，但刷新数据源仍然是全量账号；必须同时修初始化、首次显示、变化通知和持久值校正。
3. `MainWindow.refresh_account_consumers` 当前只通知 DailyTask、MultiAccountDailyTask、TestAccountSwitchTask；新增任务必须加入联动。
4. 调度代码多处硬编码 `MultiAccountDailyTask._run_daily_account(self, ...)`，日进度和失败恢复也读取每日完成键。仅通过继承并重写方法不能覆盖这些硬编码调用。
5. `DailyTask.check_weekly_garden` 在 GardenTask 正常返回后立即写入 Weekly Garden；GardenTask 内部的 `is_garden_done` 用“6000 出现次数不等于 1”判断结束，空白 OCR 也可能满足该条件。
6. 已有 `get_completion/record_completion` 使用稳定 profile_id，适合作为共享完成记录来源。现有 Weekly Garden 时间戳必须保留并兼容读取。

选择最小的共用扩展：在现有多账号调度中增加少量执行、周期、进度和结果钩子，新增乐园任务复用该调度。生产登录、别名匹配、验证、重试、退登、账号绑定与运行快照继续走现有方法，不复制约 3500 行的多账号类，也不为本次创建泛用插件调度框架。

## 四、共享完成状态和同步方式

### 唯一完成来源

以现有受保护运行状态中的 `(profile_id, 'Weekly Garden')` 完成时间为共同来源，新记录补充周标识、验证结果和证据引用。三个入口不能各自保存一份互不相通的“已完成账号列表”。

批量任务可以保存失败原因、尝试次数、批次状态，但这些不是完成依据。界面显示和账号入队前均重新读取共享完成记录；本轮内存 done_set 仅做缓存，不覆盖共享事实。

### 周周期

统一使用游戏周边界：北京时间周一 04:00，复用现有周本周期约定。时间戳转为明确时区再比较；旧无时区时间按当前项目约定的北京时间解释，无法解析或未来时间标为待复核。

周标识在账号开始时固定，任务结束写入前再核对。如果跨越周重置，停止旧周期记账，重新读取新周积分后才决定是否记录完成。不得把上一周的完成沿用到新一周。

### 三入口结果互认

| 操作 | 必须出现的结果 |
| --- | --- |
| 单账号每日完成 A1 乐园 | 独立周任务本周 A1 显示已完成并跳过 |
| 多账号每日完成 A3 乐园 | 单账号和独立周任务立即读取同一记录 |
| 独立周任务完成 A4 | 单账号、多账号每日后续都跳过 A4 乐园 |
| A1 同时属于两个序列 | 任一序列完成后，另一序列跳过 |
| 每日已完成但乐园失败/未做 | 独立周任务仍列为待做/失败，不能用 Daily Task 记录代替 |
| 独立乐园完成但每日未做 | 每日任务仍需要执行；仅跳过乐园 |
| 周任务失败后用户从每日入口完成 | 下次刷新自动化解旧失败，不继续补跑 |

旧版本同周合法 Weekly Garden 时间戳直接兼容读取，不因升级换存储键而重做。缺失、格式错误、跨周或明确存在冲突的记录显示待复核，读取游戏页后再确认。不得用账号别名或当前序列名称作为完成记录的主键。

完成事件用于尽快刷新可见卡片；正确性依赖执行前实时读取共享状态，因此窗口未打开或事件暂时未送达也不能导致重复任务。此计划保证同一受保护账号运行数据源内的互认；NAS 发布更新本身不会自动同步不同电脑的运行状态，不在本版增加远程状态合并系统。

## 五、乐园成功条件与执行流程

新增内部结果 `GardenRunResult`，至少包含 `status`（completed/already_completed/pending/failed）、`week_key`、`points`（可未知）、`verified`、`evidence_ref`。调度只在 completed/already_completed 且 verified 时跳过该账号的后续乐园执行。

账号流程：

1. 在当前序列快照中取下一候选，重新读取执行安排和共享周完成状态。
2. 已关闭或本周已完成则跳过；预算不足则结束本批次。
3. 通过现有生产流程切号，验证真实身份，绑定同一 profile_id 的账号配置。
4. 打开乐园周常页面，读取当前积分；已经达标则记录本周完成，不启动新局。
5. 未达标时执行 GardenTask；空白 OCR、加载页和无法确定的结果只能触发有限重读，不能当作达标。
6. 对局结束后返回周常页面，用两张新画面确认当前周积分达到 6000，再写共享完成记录。
7. 先持久化成功记录，再更新批量进度及 UI；写入失败时保留待复核，不把账号标成完成。
8. 恢复稳定主界面，再处理下一账号。全部完成后保留最后账号和现有退出策略。

积分达标与奖励领取分别展示。当前改动不凭积分达标宣称奖励全部领取；如现有流程尝试领取，须独立验证领取状态。证据统一经现有接口写入 okww监控室。

独立入口必须让失败返回给批量调度；不能直接调用当前会捕获错误后继续返回的 `check_weekly_garden` 然后当成功。共用底层检查返回明确结果，随每日入口可继续其他每日事项但保留乐园待处理状态，独立入口则记失败并继续下一个账号。

## 六、批量执行、失败与时间预算

- 默认按当前序列生产顺序处理；每次重启重新过滤共享已完成账号。断点以账号级完成为准，不承诺恢复到乐园局内某一步。
- 失败账号保留 profile_id、周标识、阶段、原因、尝试次数、证据引用。先处理其余账号；预算允许时本次最多补跑一次，防止无限循环。
- 达到账号数或时间预算时，停止新账号和失败补跑；剩余项为待执行，不写成失败。
- 每日进度仍使用现有命名空间；乐园进度/失败单独使用 `multi_account_garden:<week>` 与 `multi_account_garden_failures:<week>`。对旧无完整性服务路径提供独立乐园进度文件，禁止覆盖 multi_account_progress.json 的每日字段。
- 周任务不调用每日 `_mark_done` 的持久化结果，不创建 Daily Task 完成记录，不触发周本 Boss 待补检逻辑。
- 检查跨午夜、跨周、重启恢复和失败恢复中所有对 `_today`、`_daily_is_done`、每日失败记录的依赖，将必要处接入周期与完成键钩子；仅更改类名或名称文案不足以完成复用。
- 状态和错误文案随任务类型变化；明确提示“乐园失败”而非“每日失败”。
