# 深塔账号周期与失败续跑实施计划

实施状态：已随 1.97.12 实施。实际实现、测试、安装结果及倒计时 OCR 的验证限制见 [发布验证记录](../../reviews/account-task-overview-1.97.12-verification.md)。下文的基线说明保留制定方案时的历史背景。

## 目标与执行基线

目标：按游戏内特征码确认账号，按可核实的深塔赛期保存逐层进度；一层挑战失败后尝试其他合格预设，穷尽后在本赛期跳过该层并继续其他塔。程序异常不能被写成战力不足。

实施应从包含新版「游戏预设编队」的最新已发布源码开始。2026-10-05 已将主工作区与打包版 working 更新到 `v1.97.08`；主工作区原有未提交修改另存于 `pre-update-2026-10-05-main-workspace-v1.80.00` stash。实施前从当前标签建立干净工作树，避免混入历史未提交修改，也不要覆盖打包版的运行数据。

## 状态与安全规则

- 记录键：`profile_id + adversity_tower + cycle_id + tower + floor`。特征码仅用于运行开始时匹配唯一绑定的账号；记录和日志不存原始特征码。
- `cycle_id` 必须来自游戏界面可确认的赛期结束时间或稳定倒计时。先采集和复核实际界面；不能确认时 `cycle_id = unknown`，本次仍可扫描和挑战，但不能借旧记录自动跳过关卡。不得假设固定 14 天或 21 天。
- 逐层保存 `observed_state`、`attempted_teams`、`outcome`、`reason`、`observed_at`。队伍键至少含游戏预设编号与三名角色身份；同一预设换人后可视为新候选。状态区分 `completed`、`available`、`locked`、`failed_with_team`、`blocked_for_cycle`、`uncertain`；`blocked_for_cycle` 表示自动候选已穷尽，不等于游戏已完成。
- 游戏关卡扫描和完整结算页是完成状态的权威来源；旧缓存不覆盖新赛期或可靠的相反画面。识别冲突、OCR 不完整、导航/预设错误时标记 `uncertain`，不写入 `blocked_for_cycle`。
- 一次失败只排除那一支已实际挑战的队伍，返回三塔后重新扫描疲劳值、预设和全局规划，试另一支符合属性与体力要求的队伍。没有新的、已核实的候选才记录 `blocked_for_cycle`，转向右塔/中塔；跨重启不重复尝试已失败的同一队伍。提供手动「本周期重试此层」入口，供用户改变装备/练度后解除跳过。
- 账号核验失败、赛期未知、数据文件损坏、截图状态不确定时采用保守降级：不借用别的账号/赛期数据，也不自动宣称完成。存储写入使用现有原子 JSON 帮助函数，写前校验 schema；旧文件保留备份。

## 实施任务

### 1. 确认运行基线与赛期证据

1. 在最新 `1.97.xx` 源码的独立工作树核对打包版 `AutoAbyssTask.py`、`abyss_allocation.py`、账号核验模块及当前版本；记录差异，确认以哪一提交为起点。
2. 在深塔总览/周期挑战界面收集赛期结束日期或倒计时的匿名画面，验证两次读取结果能映射到同一结束点；同时用赛期切换画面证明新 `cycle_id` 会改变。不能获得稳定证据时先实现账号隔离与本次运行重试，跨运行跳过保持关闭。
3. 从现有 10-04/10-05 日志和截图构建回放样本：左塔 9/12、右塔 6/12→9/12、挑战失败、预设滚动异常和队伍校验异常。运行数据只读，不搬入测试仓库的敏感目录。

### 2. 接入账号核验

**文件：** `src/task/AutoAbyssTask.py`、`src/task/account_feature_verification.py`（仅在复用接口确需扩展时）、`tests/TestAccountFeatureVerification.py`、新的深塔集成测试。

1. 任务进入 F2 前复用 `FeatureRun(..., expected_profile(task)).begin()`，冻结 `profile_id` 与窗口/任务上下文；不另写 OCR 特征码识别器。
2. 每次读写赛期进度、选队前及结束时调用已有 guard；能安全回到显示特征码的世界画面时调用 `finish()`。结束复核不通过则暂停自动归属确认并保留待核验事件。
3. 测试唯一绑定、未绑定、重复绑定、期望账号不符、运行中绑定变化；断言不会把 A1 的关卡记录用于 A3/A4，原始码不会写入进度文件或日志。

### 3. 增加最小赛期进度账本

**文件：** 新建 `src/task/abyss_cycle_progress.py`；在 `AutoAbyssTask.py` 接入；测试 `tests/TestAbyssCycleProgress.py`。优先使用现有原子 JSON 写入函数与 `configs/` 存储方式，不增加依赖。

1. 定义读取、原子写入、赛期切换、逐层状态更新接口。保存 `profile_id/cycle_id/tower/floor`、截图核实的状态、结算结果、队伍键、时间与错误类别。限定赛期历史保留量，清理时仅删过期缓存，不动完成证据库。
2. 运行开始先检查赛期键，再扫描三塔；扫描得到的 `completed` 立即记账，`unknown` 不推断。完整胜利结算后按层保存，全部目标关卡完成才标记该账号本期深塔任务完成。已有 `completed` 层在同赛期重启时跳过，但进入游戏后的扫描仍复核实际状态。
3. 失败结算后立即写入 `failed_with_team`；持久化完成再启动另一队。若程序崩溃，重启时保留已确认的失败队伍，不重复消耗一次战斗；若写入失败则中止自动续跑并提示，避免无限重复。
4. 测试两个账号隔离、同账号同赛期续跑、新赛期自动清零、赛期未知、损坏/中断写入、已完成与失败不能互相覆盖。

### 4. 失败换队与继续其他塔

**文件：** `src/task/AutoAbyssTask.py`、`src/task/abyss_allocation.py`（若需要候选排除参数）、`tests/TestAbyssTeamPlanner.py`、`tests/TestAbyssReturnRecovery.py`。

1. 为当前关卡的 `allocate` 输入排除本赛期已失败的队伍键；沿用现有属性、疲劳值、队伍身份校验。失败后安全返回三塔，刷新预设/体力并重新规划。每次挑战前再次核对楼层和队伍。
2. 为一层设置有限状态循环：候选队伍数量是重试上限；同一队伍最多挑战一次。新队成功就更新完成并继续下一层；候选穷尽则写 `blocked_for_cycle`、注明每队失败原因、处理下一塔。预设读数不确定时保留 `uncertain`，不算候选穷尽。
3. 将游戏结算失败与 `RuntimeError`/OCR/滚动/输入异常分支分开；程序错误可局部恢复一次并重新观察，不把预设校验失败归入「打不过」。无法安全确认页面时停止输入并保留其他塔未处理状态。
4. 测试「左塔 4 层队 A 失败→队 B 成功」「队 A/B 均失败→右塔」「只有队 A→下次运行直接处理右塔」「预设或 OCR 错误→不封锁左塔」。

### 5. 修复日志暴露的预设流程故障

**文件：** 以新版 `src/task/AutoAbyssTask.py` 中 `_scan_saved_presets`、`_selected_preset_matches`、`_apply_saved_preset`、续关路径为主；新增相应图像/模拟测试。

1. 预设列表滚动用已见队列编号、列表图像和滚动条/边缘证据判断进展，发现同一页循环时停止并归类为扫描不确定；不要用固定 24 屏耗尽来伪装到底。日志限频，避免每页反复打印相同预设告警。
2. 将「预设找不到」「下方头像顺序未确认」「开战前队伍不一致」拆成可诊断结果，保存当帧证据；只有成员身份和选择态确认后才能点击开战。续关如果游戏切回编队页，先重新定位预设，再核对，而不是沿用旧页面位置。
3. 复核左塔战斗中共鸣键异常高频与角色切换超时是否为实际输出不足的重要原因；若是独立战斗缺陷，单独修复并验证，不能通过更换队伍掩盖。

### 6. 验收与发布

1. 先跑账号核验、账本、深塔编队和结算聚焦测试；再用打包版在一个已绑定账号上验证同赛期重启跳过失败队、仍继续右塔；另一个账号不继承进度。检查新赛期识别和手动重试入口。
2. 检查状态文案显示「已完成层数、未完成层、已失败队伍数、跳过原因、赛期来源/截止」；不要把部分完成显示为整期完成。确认截图和日志不泄露原始特征码。
3. 代码变更同版更新 `config.py` 和产品更新日志，按当前最新版本递增第三位；验证后提交、创建匹配的注释标签并推送分支和标签。打包发布后再检查运行日志。

## 时间顺序

用户报告本期剩余约 6 天 11 小时。先完成基线/赛期证据与账号隔离，再做逐层账本和换队，最后处理预设异常和打包验收；整个修复应在本期结束前留出至少一次真实账号回归窗口。若赛期识别证据来不及确认，先交付本次运行内的安全换队与异常分类，不启用跨运行自动跳过。

## 当前限制

现有日志没有深塔任务的特征码核验记录，无法把 10-04 与 10-05 的全部深塔运行严格归属到某个账号。日志能确认左塔第四层两次结算失败；不能仅据此断言角色强度是唯一原因。主工作区与打包版已对齐到 `v1.97.08`；实施时仍需使用干净工作树，避开主工作区保留的历史未提交文档。
