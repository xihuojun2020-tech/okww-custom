# 特征码首尾核验与初露峥嵘完成证据实施方案

状态：2026-09-13 已实施首批代码并通过离线验证，版本 1.61.00；实机验收由用户手动执行。原方案日期：2026-09-12。

实施结果与使用步骤见 [1.61.00 验收记录](../../reviews/2026-09-13-feature-verification-1.61.00.md)。下文“现状”保留方案制定时的背景，以验收记录为当前实现说明。

**Goal:** 以游戏右下角特征码确认真实账号，交叉检查每日任务所选账号，将初露峥嵘的实际完成证据归到正确账号。
**Architecture:** 在原始游戏帧的防烧屏区域进行首尾核验，以稳定账号 UUID 关联运行和证据；复用现有账号配置、完成检查及证据仓库，不新增独立活动账号下拉框。
**Tech Stack:** 现有 Python/ok-script OCR、账号配置服务和证据 SQLite 仓库，不新增依赖。
**Spec:** 本文记录本次用户批准的首尾核验规则，作为实施与验收依据。

## 一、范围和约束

- 首批接入 CharacterTrialTask；多账号每日任务以每个账号的子任务为核验边界。其他任务逐项接入，不在通用基类中强制所有任务进入游戏核验。
- 游戏特征码是唯一的自动身份依据。昵称、手机号、备用识别码只用于原有登录定位，不作为特征码识别失败的替代。
- 每日任务账号选择是期望账号；开始时冻结 profile_id 与绑定特征码，UI 后续更改不改变本轮归属。组选择不可冒充具体账号。
- 不识别头像或角色名称；保留5/6人配置、归一化点击以及现有奖励判定。
- 使用本地 .venv；不修改 site-packages。实现代码后按仓库规则更新版本、同步文档、验证、提交、打标签、推 GitHub，并单独发布 NAS 更新及校验。

## 二、现状与修改文件

- config.py: blur_area 定义单一右下角区域；复用，不为核验改变现有模糊范围。
- src/account_identity.py: 已有 game_feature_code 字段和 strict_feature_code 参数，但特征码不命中仍回退手机号匹配。新增独立精确解析入口或明确修正严格模式，并检查既有调用兼容性。
- src/config_integrity.py、src/account_config_editor.py、src/account_rebind_service.py: 复用绑定、校验和账号 UUID，增加重复绑定拒绝及在运行中变更绑定的失效处理。
- src/gui/AccountConfigTab.py: 将“只记录、不参与任务”说明更新为真实用途，提供读取并确认绑定流程；修改翻译时同步目录与编译产物。
- 建议新增 src/task/account_feature_verification.py: 原始帧读取、区域裁剪、稳定识别、核验结果，不处理 UI 与 NAS。
- src/task/CharacterTrialTask.py: 开始前核验、最终状态复核后核验、运行结果与截图关联。
- src/task/MultiAccountDailyTask.py: 暴露明确的期望 profile_id；后续按账号接入首尾核验，切号测试继续复用生产流程。
- src/gui/CompletionCheckTab.py 及现有证据仓库服务：新增初露峥嵘项目的稳定键，复用历史/待核验/图片持久化，不挪用旧活动项目。
- tests/TestCompletionEvidence.py、tests/TestCharacterTrial.py、新增 TestAccountFeatureVerification.py：集成和严格匹配测试。

## 三、一次核验的定义

输入：冻结的期望 profile_id、绑定值、运行编号、阶段 start/end。
1. 获取有效的新鲜游戏客户区原始帧，检查窗口、帧尺寸与采集失败；拒绝缓存重复帧冒充多次观察。
2. 按 blur_area 的范围裁剪；1080P 为(1688,1054,224,25)，2K 为(2250,1405,299,34)。允许仅为OCR等比放大，不修改原图。是否需要小幅扩大区域由真实样本测试决定。
3. 解析“特征码”标签后的完整数字字符串。保持字符串，不转换整数，不猜漏位，不用部分匹配或昵称回退。位数规则先依据绑定和真实样本确认，不擅自认定永远固定10位。
4. 在最多5秒的短窗口内至少3个新鲜帧连续完整结果相同；冲突或空结果清零连续计数。5秒是循环预算，不承诺中断正在执行的OCR。
5. 返回 verified/unreadable/unbound/mismatch/ambiguous，携带核验时间、来源区域、分辨率、帧证据信息；公开日志只显示账号标签和结果，不输出完整特征码。
6. 配置首次绑定从稳定读取结果创建候选，由用户确认归属；不能在运行时自动学习并覆盖绑定。已绑定重复值禁止自动归属。

## 四、任务流程

开始：进入可核验的游戏画面→获取期望账号→稳定读取特征码→严格映射账号→与期望值一致→冻结运行上下文→执行初露峥嵘。
- 已知但不一致：停止，显示计划A3/实际A4，不自动换归属继续。
- 未绑定、重复绑定或无法读取：任务尚未执行，保持待核验并说明原因。
- 单独启动活动且无具体期望账号：若特征码唯一绑定，使用该实际账号，并明确显示；若每日任务配置明确选了其他具体账号则按冲突处理。

结束：现有最终奖励状态检查通过→采集最终画面与结束核验帧→特征码与开始一致→保存脱敏截图及核验元数据→证据提交成功后更新完成状态。
- 结束核验不通过：保存任务结果和截图为待核验，不能自动确认完成，也不伪装任务执行失败；保留两种状态的区别。
- 五人配置只证明所配置五个位置已完成，六人配置同理；不得宣称自动发现并覆盖所有角色。
- 异常/停止仅保存部分进度或失败证据，不产生成功完成记录。
- 最终画面与核验尽可能来自同一取帧序列；运行中重新登录、程序切号、窗口更换或绑定变更使上下文失效。
- 首尾核验不证明过程中从未人工切号；这是本版已接受的边界。程序控制的切号需互斥，人工切号无法仅靠首尾彻底排除。

## 五、存储与完成检查

复用账号 UUID，不使用可改名的A3作为永久主键。元数据包含 run_id、profile_id、task_key、版本、起止核验时间、验证状态、配置人数、各位置结果、完成截图引用与保存状态。完整特征码仅留在已有受控账号配置及确有必要的受控记录，不散落日志；导出仍沿用现有脱敏。
完成证据先成功落盘及索引，再更新完成时间；若跨存储不能事务提交，记录可恢复中间状态，并按run_id幂等恢复，不能先打勾后丢图。旧证据不追认、不改归属、不覆盖。
NAS上传独立于本机完成判定：本机证据持久化成功后可完成，NAS失败显示待上传并重试，不能为网络故障重复做游戏任务。
界面显示“当前账号A3｜特征码已核验”“期望A3｜一致”；活动项目进入完成检查的新增截图更新组，不给常驻试用强加每日重置。
