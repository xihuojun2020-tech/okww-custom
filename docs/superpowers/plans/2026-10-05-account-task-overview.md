# 账号任务总览与 ALAS 式分类导航：设计稿及实施方案

日期：2026-10-05。状态：用户批准后已实施；发布版本 1.97.12。基线版本：1.97.11。实施与验证记录见 [账号任务总览发布验证](../../reviews/account-task-overview-1.97.12-verification.md)。

**目标：** 保留账号配置页顶部账号选择，在下方使用 ALAS 式左侧分类导航、右侧总览／设置切换，展示每个账号真正选择的任务、当前周期状态与执行时间。

**架构：** Qt 页面展示正式账号配置、现有完成记录、材料领奖账本和执行器状态的统一快照。共享北京时间周期计算同时服务执行器与界面。周期变化只更新任务是否到期，不清除历史时间、累计材料或选择配置。

**技术：** 现有 PySide6、qfluentwidgets、AccountRepository、ConfigIntegrityService；不引入 Web 服务或额外数据库。

## 一、已经确认的范围

- 顶部账号下拉、新建账号、草稿预览／保存／丢弃保持现有操作语义。
- 下方两列：左侧大类及具体任务；右侧切换总览与设置，不常驻第三列。
- 账号序列管理也放入左侧分类，在右侧设置区域显示，避免外层序列面板挤占总览高度。
- 具体参照 ALAS 的分类展开、总览分组、任务设置跳转，采用当前程序的统一主题。
- 每日北京时间 04:00 更新状态；每周周一 04:00 更新状态。
- 到点只更新状态；不会自动启动游戏或账号任务，继续由用户启动现有多账号入口。
- 日常、周常展示正式配置及执行状态；深塔展示状态但仍单独启动，不随多账号每日入口执行。
- 海墟、活动等任务也纳入总览，仅作标记与提醒，用户手动标记完成；勾选它们绝不触发自动执行。
- 手动提醒任务每项可选每日、每周、自定义下次重置时间、不自动重置；尚未设置时默认不自动重置。
- 不改此前已确认的每日顺序、体力优先保障活跃度、材料累计、最终活跃度不足报错等规则。
- 全部账号旧选项保持原值；旧凝素账号没有新目标时沿用旧刷法；不恢复培养目标或库存扫描。

## 二、本次源码调查结论

### ALAS

- `E:/AI work/alas/module/webui/app.py` 的 `alas_set_menu()`：总览入口、可展开的大类、具体任务入口。
- 同文件 `alas_set_group()`：点击任务后切换右侧设置。
- 同文件 `alas_update_overview_task()`：展示 running／pending／waiting，卡片提供“设置”按钮。时间来自 `next_run`。
- `E:/AI work/alas/module/config/config.py` 的 `get_next_task()`：先排除未启用任务，到期任务按优先级进入 pending，未来任务进入 waiting。
- 本方案采纳上述导航和分组原则；按用户要求保留手动启动。“下次可执行时间”不承诺程序会到时自动运行。

### 当前程序

- `src/gui/AccountConfigTab.py`：现有顶部账号选择、身份字段、提醒、日常／周常等折叠分组；独立草稿与修订冲突检查已存在。
- `src/config_integrity.py`：`record_completion()`、`get_profile_completions()` 和 `get_progress()`／`update_progress()` 已提供按稳定 profile_id 的原子运行记录。
- `src/task_status.py`：现有状态桥包含账号显示名、阶段和详情，但缺少可靠的结构化子任务 ID、已核验 profile_id、run_id。
- `src/evidence/service.py` 和 `repository.py`：已有整次执行的开始、结束与结果；`returned` 只表示正常返回，不能等同所有任务完成。
- `src/evidence/model.py`：证据已有明确的 UTC+8 和凌晨 4 点周期规则。
- `src/task/DailyTask.py`：聚落检查点已经使用 4 点游戏日，并包含所选列表的摘要；材料与活跃度有实际核验入口。
- `src/task/MultiAccountDailyTask.py`：`_today()`、`_current_progress_period()`、启动时 `_progress_date` 及部分完成判断仍使用自然日／字符串前缀。必须统一，否则 UI 与账号跳过逻辑会冲突。
- `weekly_boss.py`：已经区分周一执行与周日复检；`weekly_garden.py` 已支持周一 04:00 游戏周。
- 凝素、首领材料已经有 confirmed／pending／cancelled 领奖账本，可直接用于进度与待核验展示。
- `AccountReminderPanel.py` 当前只是提醒和备注。勾选提醒不能被解释为启用自动任务或证明任务完成。
- 深塔现有扫描／战斗逻辑与此前赛期进度方案可复用，但本次未发现已经落地的 `abyss_cycle_progress.py`。赛期、逐关和失败队伍账本必须作为深塔纳入总览的配套工作。

- 原有提醒和备注完整保留；具体海墟／活动任务提供独立的“显示提醒”与“手动标记完成”，不占自动任务待执行数量。原来勾选“活动”大类不等于升级后启用全部活动子项。

### 两列宽度与滚动

- 导航建议 180–220 个逻辑像素；右侧占剩余宽度。最终取值用实际主窗口与缩放截图确认。
- 顶部账号与草稿操作固定可见；导航和右侧内容各自滚动，设置页滚动位置按分类记忆。
- 宽窗口总览可将“运行中／待执行”与“等待中／已完成”排成卡片列；窄窗口总览各组纵向排列，仍保持整体两列结构。
- 不强制复制 ALAS 的边框、字体或密集程度；复用当前主题的颜色、字体、间距与控件。

## 四、总览状态与时间

| 分组 | 判断依据 | 典型文案 |
| --- | --- | --- |
| 运行中 | 当前执行器 run_id、已核验 profile_id、task_id 一致 | 残像聚落：正在挑战；开始 21:30，耗时 02:15 |
| 待执行／待办 | 已启用、到期、本周期无有效完成记录；执行任务与仅提醒任务分区并注明类型 | 活跃度与奖励：等待手动启动；海墟：仅提醒、等待手动处理 |
| 等待中 | 尚未到可执行窗口，或本轮资源不足但累计目标仍保留 | 周本：周日 04:00 可复检；凝素：今日体力不足，下次继续 |
| 需要处理 | 报错、消费待核验、记录无法读取、深塔本期受阻 | 左塔第四关：可用队伍均失败，本期跳过；其余塔仍可执行 |
| 已完成 | 当前周期／当前目标有对应的明确成功依据 | 今日聚落已完成；首领目标 5/5；本期深塔目标已完成 |

每张卡片按适用情况展示：任务名、当前状态、目标／进度、最近开始时间、最近完成时间、下次重置或可执行窗口、执行范围／来源及错误摘要。

- 所有时间标注北京时间，采用 `MM-DD HH:mm`；展开详情显示年份、秒和 UTC+8。
- 尚无记录显示“未记录”，不显示虚构的时间或预计完成时间。
- “下次重置”与“下次可执行”分别标注；手动模式不称“将在该时刻自动运行”。
- 资源不足没有精确下一次执行时间时显示“下次手动启动继续”，不估计体力恢复后自动运行。
- 已完成统计按真正启用的周期任务计算；有限材料目标另显示累计进度，不用它们阻止每日活跃度结果成立。提醒完成数量单独统计，不影响多账号日常的完成判断。
- 活跃度以实际读取结果判定；未打某模块不能推出活跃度不足 100。
- 显示其他账号正在运行时，仅在页首给出运行账号摘要，不把它记入当前所选账号的“运行中”。

### 必须区分的完成依据

1. 残像聚落：全部已选聚落的匹配检查点；空列表显示未启用。列表变化后旧列表检查点不能证明新列表完成。没有单聚落证据时不虚构逐地点完成。
2. 活跃度／奖励：分别记录实际复核值和宝箱领取结果；100 分与奖励已领取分开显示。
3. 无音区：作为长期启用安排显示；当日结束且资源／执行结果明确时可显示“今日安排已结束”，不能显示“长期目标全部完成”。
4. 凝素／首领：以已确认领奖累计为依据，不能把子任务正常返回或泛化完成时间当目标达标。
5. 周本：本周剩余次数、周一检查、周日复检分开；周日到期出现“待复检”，不抹掉本周已刷完的事实。
6. 深塔：当前真实赛期内按塔／关卡记录；受阻、失败、识别不确定不等于完成。

## 五、北京时间周期计算

建议增加无 Qt、无游戏输入的公共 `src/game_period.py`：

- `game_day_key(now)`：把时间转 UTC+8，减 4 小时后取日期。
- `game_week_key(now)`：取该游戏日所在周的周一日期。
- `next_daily_reset(now)`／`next_weekly_reset(now)`：返回明确的下一边界时间。
- `parse_legacy_time(value)`：兼容旧无时区记录；对本项目历史时间按北京时间解释并注明旧记录来源，异常／未来时间不作为完成依据。

执行器、证据、周常保留现有对外方法，但内部调用公共函数，避免 GUI 单独维护算法。

例：10 月 6 日 03:59 属于 10 月 5 日游戏日；10 月 6 日 04:00 起属于新游戏日。周一 03:59 仍属于上一游戏周。

- 重置是读取时比较周期键，不是到点删除完成记录。关闭程序跨越重置，重新打开即可正确显示。
- GUI 可见时更新运行状态；周期边界、窗口重新激活、系统从休眠恢复后重新计算。
- 当前任务跨越 04:00 时沿用执行器的周期保护；在安全节点结束旧周期批次。旧周期已领奖计数永久保留，新周期完成需要新的有效依据。
- 运行中任务不因界面时钟翻日直接移入待执行并复制一份。
- 多账号旧自然日断点不能直接当新游戏日完成证据；保留原数据，优先用真实完成时间判断。无时间依据的旧 done_set 标记为旧记录待复核。
- 游戏周、每日和目标计数是独立维度：凝素／首领跨日跨周累计；不会每周一重置有限目标。

## 六、数据与刷新设计

### 数据来源

正式配置：`AccountRepository` 中已保存的账号任务方案与身份。

完成时间：`ConfigIntegrityService.completed_at`。

目标进度：现有凝素、首领、周本账本及新增深塔赛期账本。

运行状态：现有 executor 与 `task_status`；补充结构化 profile_id、task_id、run_id 和开始时间。

图片及整次运行详情：现有 EvidenceRepository。截图人工确认和执行器核验显示来源，不让截图正常保存等同任务成功。

手动提醒：使用现有账号 extensions 保存逐项提醒配置，运行状态保存手动完成时间、周期键和来源 manual。只对提醒任务提供“标记完成／撤销完成”；撤销保留最近手动标记时间与来源，当前状态恢复待办。按钮明确写“手动标记”，不伪造程序核验结果，不修改 `Daily Task`、材料账本或深塔关卡通关记录。提醒配置变化走草稿保存，完成操作立即写入独立运行状态，不能借此保存其他未保存配置。

### 最小增补

新增 `src/account_task_state.py`，负责把上述数据归一为任务快照；输入已保存方案、运行数据和当前时间，输出纯数据，不控制游戏。

需要补充的任务最近一次执行结果通过现有原子 `update_progress()` 存入 `task_state_v1:{profile_id}`，每条至少包含：task_id、目标／配置摘要、period_id、run_id、started_at、finished_at、result、reason。材料累计仍留在原账本，避免双写计数。

- 活跃度结果补充 actual_points、核验时间及奖励领取状态。
- 任务配置摘要只包括决定任务目标的字段；账号显示名改动不会使完成记录失效。
- 状态卡片由记录推导，不另存 GUI 的“已完成”布尔值。
- 开始／成功／资源不足／失败在正式执行路径相应结果处写入；关闭 UI 不影响记录。
- 损坏或读取失败显示“记录无法读取／需要处理”，不能降级成已完成或擅自清空数据。
- 状态记录写入失败必须明确提示；完成状态不确认，不盲目重跑可能已经发生的消费。
- 重启后发现孤立 running 记录，显示“上次运行未确认结束”，除非当前执行器确有对应 run_id。

### GUI 更新

- 新增 `src/gui/AccountTaskOverview.py`，只负责总览分组、卡片和跳转。
- 复用 `BackgroundOperation` 读取配置／运行数据，捕获 profile_id 与请求序号；旧账号的异步返回不得覆盖新账号。
- 当前可见页约每秒更新执行器耗时；持久记录按版本／任务结束事件更新，可用现有低频定时读取兜底。
- 隐藏页暂停持续轮询，重新显示时刷新；避免每秒重读整份账号仓库。
- 不在状态刷新中调用整页 `_render_form()`。输入焦点、展开位置、数字输入、滚动位置与未保存草稿必须保留。

## 七、深塔接入

1. 每账号独立选择在总览显示深塔及目标塔／关卡，默认旧账号不自动新增勾选。深塔卡片固定标注“单独启动”，不会成为多账号每日执行队列的一项。
2. 正式执行前复用特征码核验，把永久账号身份关联到稳定 profile_id；不以昵称或下拉显示文字归属结果。
3. 从游戏读取赛期信息／结束时间。原先“六天十一小时”仅是当时观测，不能在新版本中硬编码为实时倒计时。
4. 有可信赛期键才进行跨运行跳过。无法识别赛期则显示“赛期待核验”，不得猜测固定两周或三周而错用旧记录。
5. 状态按 `profile_id + cycle_id + tower + floor` 保存，包含已确认完成、失败队伍、候选耗尽／本期受阻、识别不确定、时间与原因。
6. 左塔四关队伍 A 打不过：排除该队并尝试符合条件的 B；无候选时记录本期受阻，处理右塔。页面相应显示部分完成和受阻明细。
7. OCR、预设滚动或队伍选择故障归为执行异常，不记录成“队伍实力不足”。
8. 新赛期只让新赛期目标重新待执行，保留旧赛期历史。预设／阵容发生有意义改变后允许用户明确重新评估受阻关卡。
9. 复用原深塔入口，增加当前已核验账号归属和正式配置读取；总览提供“设置／记录／前往深塔任务”跳转。跳转不直接启动；不能在浏览 A3 时把游戏当前 A1 的结果归到 A3。
10. 多账号日常及其退登路径保持现有执行范围；新增深塔展示不影响每日任务完成判定。

### 海墟与活动提醒

- 所有提醒账号隔离；可选择当前需要关注的具体项目，未选择的项目留在设置页。
- 总览卡显示“仅提醒、不自动执行”、最近手动完成时间、当前周期与下次重置。
- 勾选表示显示提醒；“手动标记完成”更新状态，两种操作明确分开。
- 允许撤销误标。只改变提醒状态，不创建真实通关、奖励已领取或截图核验记录。
- 已确认每项周期可选每日 04:00、每周周一 04:00、自定义下次重置时间、无自动重置；日期均按北京时间。自定义时间是一次明确边界，到点恢复待办后需要设置下一次时间，不猜测活动循环。
- 未设置周期或无法确定下次活动周期时，完成标记保持，直到用户撤销／设置下一边界。到活动结束时间显示“已结束”，不能把截止日当作新一期开始。

## 十、验收场景

| 场景 | 必须看到的结果 |
| --- | --- |
| 今日 22 点完成，次日 03:59 打开 | 仍属于前一游戏日的已完成 |
| 次日 04:00 打开／窗口恢复 | 已启用每日任务进入新周期待执行，旧完成时间保留 |
| 周一 03:59／04:00 | 在 04:00 才切换游戏周 |
| 周一周本次数耗尽，周二打开 | 本周已刷完，等待周日复检，不新增每日周本 |
| 周日 04:00 | 出现待复检，原本周次数完成事实保留 |
| 凝素目标只完成一半 | 次日继续剩余累计，不归零；日常完成与目标完成分别显示 |
| 首领目标达到上限并自动关闭 | 从未来待执行移除，保留达标记录 |
| 无聚落勾选，但实际活跃度 100 | 聚落未启用；活跃度按实测显示 100，不推断不足 |
| 消费事件 pending | 显示待核验；不计入目标完成，也不安排后续盲目消费 |
| 深塔左四关全队失败 | 本期受阻及队伍原因可见，右塔继续；不显示全塔已完成 |
| 深塔赛期无法识别 | 赛期待核验，旧周期记录不用于确定跳过 |
| 快速 A1→A3→A4 | 旧异步返回不串号，当前任务只归属真实已核验账号 |
| 海墟／活动手动完成 | 进入已完成并注明手动来源；不执行游戏、不影响每日完成 |
| 提醒撤销完成／到期重置 | 恢复待办，旧完成时间保留，材料与自动任务记录不变 |
| 更新旧版本配置 | 既有勾选全部保持；海墟、活动不进入账号执行调度 |
