# 完成检查更新规则、活动名称与账号紧凑布局方案

状态：已实施，版本 1.60.00；验证和发布结果见文末。依据：用户 2026-09-12 两次需求与实施确认。

## 1. 目标与方案选择

完成检查按三类规则展示：每日更新、每周更新、新截图更新。沿用现有证据库、账号 UUID 和界面刷新机制，通过统一项目目录定义名称与周期。相比仅改界面文案，此方案同时解决底层查询与历史记录兼容；无需建立第二套完成记录系统。

“更新”指当前展示有效期更新或新证据替换，不是删除原图，也不是到点自动截图。自动截图仍由现有任务触发，手动截图仍由用户操作。没有新证据时显示“本日/本周暂无记录”，不能推断未完成。

## 2. 分类与刷新规则

| 分组 | 项目 | 更新方式 |
| --- | --- | --- |
| 每日更新 | 活跃度、残像聚落、战令 | 北京时间每天 04:00 切换游戏日，只汇总当日证据 |
| 每周更新 | 周本、每周乐园 | 北京时间每周一 04:00 切换游戏周，只汇总本周证据 |
| 新截图更新 | 四项当前活动、深塔、海墟、矩阵 | 不随日/周清空；保存成功的新截图更新当前展示 |

04:00 沿用现有 `src/evidence/model.py` 游戏时间规则。程序关闭时不依赖定时执行；下次启动、打开页面或跨周期刷新时重新计算。页面打开期间复用现有周期检测与 service revision 检查。

日/周类当前无证据时保留历史入口，可提示最近记录日期，但旧记录不计入本周期。周本跨日仍保留本周记录。活动等跨日、跨周持续展示最新截图及拍摄时间。

## 3. 截图与状态的关系

当前 `summarize` 优先选择历史明确结果，可能让新截图被旧“已完成”遮住。调整为分别选择“最新截图”和“有效完成结论”。

- 同账号同项目内按采集时间排序，相同时间以入库序号稳定排序；补传旧截图不覆盖较新截图。
- 新截图保存成功后展示该图。新图无法可靠识别时显示待核验，旧结论在历史中保留，不冒充对新截图的判断。
- 手动确认绑定具体证据 ID；可更新该截图状态，不能把对旧图的确认套在新图上。
- 只有完成记录而没有截图时明确显示“仅有完成记录”；截图失败不得清空已有图片或伪装产生新截图。
- 日/周类继续保留本周期可信完成记录，但若其时间早于新截图，界面单列记录来源和时间，避免混成一个结论。
- 同一证据自动结果与手动确认矛盾时显示冲突；后续不同时间截图的正常变化不永久标记为冲突。
- 新截图更新类的“仅看待处理”根据当前有效状态工作，不能因没有周期 ID 而始终显示已完成项。

核对范围：账号待办复选框与摘要、完成检查卡片与筛选器、手动截图选择器、活动页任务卡片与占位卡、相关任务标题与通知、导出中的项目名称、翻译与当前使用说明。当前入口不再出现“活动1/2/3”；历史文档与旧日志不重写。尚未实现自动执行的活动保留原有手动截图能力，不因名称调整宣称支持自动执行。角色试用保留其独立身份，不强行改名为四项活动之一。

账号提醒补齐为与完成检查相同的 12 项，按三类分组：3 项每日、2 项每周、7 项新截图。提醒只影响提醒展示和筛选，不改变执行开关或任务安排。

## 5. 旧数据兼容

现有残像聚落和战令 `period_id` 为 NULL，直接改规则会使旧数据查询失配。增加一次性、可重复执行的事务迁移：

1. 先制作一致性数据库备份；根据原始带时区 `captured_at` 计算两个项目的游戏日。
2. 同步数据库查询列及 metadata 中周期字段，保持证据 ID、原图路径和采集时间不变。
3. 时间无效的记录不猜测归属，保留历史并报告迁移异常；事务失败回滚，不形成半迁移数据。
4. 旧 `activity_1/2/3` 无法凭序号确定真实活动，不自动对应正式名称。历史保留原始标识；界面统一归入“旧版活动记录（待归类）”。
5. 旧提醒同样保留为待归类信息，账号正常打开与保存时不得悄悄丢失；允许用户显式选择对应正式活动或移除旧提醒。新设置仅使用正式活动标识。

## 6. 账号页面间距

实施时进一步确认：现有局部 `compact_settings` 已将设置行上下收紧为各 4px，仍有 56px 折叠标题和分组边距叠加。本次复用该方法，仅账号页面启用进一步紧凑模式。

建议账号页面启用局部 compact 参数，共享组件默认保持原值：

| 位置 | 建议值 |
| --- | --- |
| 设置行上下内边距 | 各 3px，原局部样式为各 4px |
| 设置行之间 | 2—4px |
| 分组之间 | 分组底部 4px，加外层布局间距 |
| 折叠标题最小高度 | 40px，文字换行时允许自然增高 |
| 标题到内容距离 | 2px |
| 同行控件横向距离 | 8px |

提醒在可用宽度足够时两列，窄窗口一列，四个长活动名称完整显示。合成账号展开身份信息与提醒后，在同样字体和尺寸下内容高度从 1535 降至 1319 逻辑像素，减少 216（约 14%）。保留字体大小、点击区域、帮助文案与校验提示；长文本、错误提示和高 DPI 不强制固定行高。保存/丢弃草稿、只读身份字段、折叠状态与单层滚动保持现有交互。

## 9. 复制截图与未来微信发送（用户第 10 项补充）

### 本次纳入：复制原图

- 完成检查截图卡片、图片预览提供“复制图片”，右键菜单提供同一操作。
- 将选中证据的原始图片写入系统剪贴板，而不是文件路径、缩略图或界面卡片截图；用户可切换微信按 Ctrl+V 粘贴。
- 操作成功提示“图片已复制”；无截图、图片缺失或读取失败时给出明确提示，不误报成功，也不覆盖原剪贴板。
- 当前记录和历史记录都可以复制，复制操作不更改完成状态或证据归属。首版一次复制一张；多张图片的剪贴板兼容性不作隐含承诺。
- 读取使用证据仓库的路径解析，复制入口共用一个实现；用 Qt 图片与剪贴板接口，不增加独立剪贴板依赖。
- 验证原图尺寸及像素内容、历史图选择、缺图处理、账号切换后的图片归属；微信实际粘贴由用户手动验收。

### 后续阶段：按账号定向发送微信

目标示例：游戏账号 A1 的截图发送到用户为 A1 明确绑定的微信联系人。绑定保存于稳定账号 UUID 下，账号改名或重排不改变收件人；不能仅凭同名“A1”搜索并直接发送。

未来账号配置可增加“截图接收人”，显示微信收件人的可核验身份及备注。两个账号允许显式绑定同一联系人；未绑定、存在同名歧义或收件人无法核验时停止发送，不猜测目标。

第一阶段建议提供“发送本张／发送选中截图”，发送前展示游戏账号、微信收件人和图片数量。后续如启用自动发送，另行保存用户明确设置的触发时机、项目范围及授权，不把本轮的未来需求视作立即发送消息的授权。

发送以证据 ID 和收件人绑定区分记录，记录成功、失败与结果未知；结果未知不盲目重试，避免重复发送。先保存本地证据，再尝试发送，发送失败不阻止游戏任务完成或丢失截图。旧图补传默认不触发自动发送。

微信接入方式在后续阶段依据实际客户端及可用接口验证；本轮只实现可独立使用的复制能力，不提前承诺后台自动发送可用，也不部署微信自动化。当前设计保留稳定账号 UUID、证据 ID 与原图读取接口即可，无需预先建设发送队列。
