# 钢琴小游戏按键高亮识别实施方案

> **2026-09-09 实机规则修正（最高优先级）：** 任一时刻只有一个按键高亮，按下后才出现下一键；每段通常按1—7次，期间可能出现剧情或转场。任务只接受单键高亮，按后停顿再继续识别；不按次数结束，界面消失时持续等待，直到用户手动停止。此规则取代下方所有多键/组合键设计。

> **2026-09-08 用户补充（优先于下文历史单键规则）：** 参考图已提供，原始大小 2560×1440，当前可见 S 金环；实际可能同时有两个或更多按键高亮。下文“唯一候选”“多个高亮暂停”和第一/第二名分差门槛不再适用于新需求。实施以[多键详细执行方案](2026-09-08-piano-key-highlight-execution.md)为准：逐键 ON/OFF/UNCERTAIN 判断、逐键连续确认和去重、同批组合按下并释放全部键。下文保留为最初设计历史，不作为多键实现指令。

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不依赖游戏内部接口的前提下，从屏幕图像判断当前需要按下的钢琴键，并将高亮位置映射为键盘字母。

**Architecture:** 使用整屏截图中的固定比例区域作为钢琴 UI 感兴趣区域（ROI），将三行按键拆成 21 个检测单元。每个单元通过亮度、颜色饱和度、黄色光晕和与历史帧的差异计算高亮分数；连续帧确认后输出唯一键位，输入层再执行按键并等待高亮状态变化。

**Tech Stack:** 现有 BitBlt/WGC 截图服务、OpenCV/Numpy 图像处理、现有键盘输入封装、Python `unittest` 离线回放测试。

**Spec:** 用户提供的 2560×1440 截图；目标是识别中音区第二个按键的 `S` 状态。该方案只描述理论实现，不包含本次代码修改或游戏实测。

## Global Constraints

- 仅支持 PC 游戏画面，不使用安卓模拟器或游戏内部注入接口。
- 只读取屏幕图像，不读取进程内存、不修改游戏文件、不注入 DLL。
- 兼容 16:9 的 1920×1080、2560×1440 等分辨率，所有坐标使用归一化比例。
- 默认使用截图识别；WGC/BitBlt 的选择沿用现有截图服务，不新增截图后端。
- 输入动作必须经过连续帧确认，禁止单帧误识别直接发送按键。
- 识别不到、同时高亮多个或高亮置信度不足时，暂停输入并记录诊断信息。
- 理论验证使用离线截图和回放，不操控真实游戏。

### Task 1: 建立钢琴 UI 的比例坐标模型

**Files:**
- Create: `docs/assets/piano-key-layout.md`（记录模板和比例坐标）
- Modify: 本方案不指定代码文件；实际开发时应在现有截图/输入任务边界内新增识别模块
- Test: 离线截图坐标测试

**Interfaces:**
- Consumes: 截图宽度 `W`、截图高度 `H`。
- Produces: 三行按键 ROI，以及每行七个键的中心点和检测框。

- [ ] **Step 1: 以 2560×1440 截图建立参考坐标**

  参考图中三行按键从左至右均为 7 个键。不要保存绝对像素作为最终配置，应记录为比例值：

  ```text
  x_ratio = x_pixel / 2560
  y_ratio = y_pixel / 1440
  width_ratio = width_pixel / 2560
  height_ratio = height_pixel / 1440
  ```

- [ ] **Step 2: 生成分辨率无关的检测框**

  运行时根据当前截图尺寸恢复像素坐标：

  ```text
  x_pixel = round(x_ratio * W)
  y_pixel = round(y_ratio * H)
  ```

  三行的按键顺序固定为：

  ```text
  高音：Q W E R T Y U
  中音：A S D F G H J
  低音：Z X C V B N M
  ```

- [ ] **Step 3: 保留检测框内缩边**

  每个检测框向内缩 15%～25%，避开相邻按键、横线和键帽文字，只保留圆点及其外圈光晕区域。检测框不能覆盖相邻按键中心。

- [ ] **Step 4: 增加 ROI 有效性检查**

  如果当前画面宽高比偏离 16:9 超过 3%，或 21 个检测框大部分处于画面外，则停止识别并记录“钢琴区域无效”，不发送任何按键。

### Task 2: 设计高亮检测算法

**Files:**
- Create: 钢琴高亮检测算法模块（实际开发时放入现有任务模块或独立 `src/` 工具）
- Test: 高亮/非高亮/过渡帧离线样本测试

**Interfaces:**
- Consumes: 一帧 BGR/RGB 图像，以及 21 个检测框。
- Produces: `CandidateKey(row, index, key, score, features)` 或“无候选”。

- [ ] **Step 1: 对每个检测框提取颜色和亮度特征**

  每个单元至少计算以下特征：

  ```text
  mean_luma          区域平均亮度
  max_luma           区域最高亮度
  warm_ratio         黄色/金色像素比例
  saturation_mean    平均饱和度
  halo_ring_score    圆点外圈光晕强度
  delta_from_base    与非高亮基准帧的差异
  ```

- [ ] **Step 2: 使用颜色空间组合判断**

  优先将图像转换到 HSV 或 Lab。黄色光晕通常表现为较高亮度、较高饱和度和偏暖色相；不要只使用单一 RGB 阈值，以降低不同画面滤镜和后处理对识别的影响。

- [ ] **Step 3: 计算综合高亮分数**

  理论分数可定义为：

  ```text
  score = 0.30 * normalized(halo_ring_score)
        + 0.25 * normalized(warm_ratio)
        + 0.20 * normalized(mean_luma)
        + 0.15 * normalized(delta_from_base)
        + 0.10 * normalized(saturation_mean)
  ```

  权重不是固定结论，首次实现应通过离线截图校准；最终以“正确键与第二名之间的分数差”作为置信度，而不是只看绝对分数。

- [ ] **Step 4: 识别唯一候选**

  取分数最高的候选 `best` 和第二高候选 `second`。只有同时满足以下条件才输出：

  ```text
  best.score >= absolute_threshold
  best.score - second.score >= margin_threshold
  best 的圆点/光晕形状通过检查
  ```

  否则返回 `ambiguous` 或 `no_highlight`，等待下一帧。

### Task 3: 增加时序确认和按键状态机

**Files:**
- Modify: 钢琴任务的识别循环和输入调度
- Test: 时序状态机测试

**Interfaces:**
- Consumes: 每帧候选结果和输入器。
- Produces: 稳定键位事件，例如 `KeyEvent(key='S', row='middle', confidence=0.91)`。

- [ ] **Step 1: 连续帧确认**

  默认要求同一键位连续 2 帧识别一致；截图间隔建议 30～80 ms。若游戏动画较快，可降为 1 帧但必须提高分数差和绝对阈值。

- [ ] **Step 2: 按键后等待状态变化**

  发送 `S` 后进入 `WAIT_CHANGE` 状态，要求原高亮单元分数下降，或下一高亮键连续出现，才允许发送下一键。避免同一高亮持续期间重复按键。

- [ ] **Step 3: 设置超时和重置条件**

  单个按键等待超过 1～2 秒仍无明确高亮时，进入暂停状态并保留截图；连续 3 次出现多候选或无候选时，重新定位 ROI，而不是盲目输入。

- [ ] **Step 4: 明确状态转移**

  ```text
  LOCATE_ROI
      ↓ ROI 有效
  WAIT_CANDIDATE
      ↓ 同键连续确认
  KEY_CONFIRMED
      ↓ 发送一次按键
  WAIT_CHANGE
      ├─ 高亮变化 → WAIT_CANDIDATE
      ├─ 超时     → RECHECK_ROI
      └─ 多次异常 → PAUSED + 诊断
  ```

### Task 4: 键位映射和输入安全

**Files:**
- Modify: 现有键盘输入封装的调用层
- Test: 键位映射和重复输入测试

**Interfaces:**
- Consumes: 行号 `0..2`、列号 `0..6`。
- Produces: 仅允许集合 `{Q,W,E,R,T,Y,U,A,S,D,F,G,H,J,Z,X,C,V,B,N,M}` 中的单个按键。

- [ ] **Step 1: 使用显式映射表**

  不根据 OCR 字符临时拼接键名，使用固定映射表；这样可以防止 `O/0`、`I/1` 等 OCR 混淆扩散到输入层。

- [ ] **Step 2: 输入前做白名单校验**

  任何不在 21 键白名单中的结果都丢弃，并写入诊断日志；禁止将原始 OCR 字符直接传入键盘接口。

- [ ] **Step 3: 保证按键成对释放**

  输入封装必须保证 `key_down` 后一定执行 `key_up`，异常退出时统一释放所有已按下按键。

### Task 5: OCR 备用和异常诊断

**Files:**
- Modify: 识别诊断日志/截图证据模块
- Test: OCR 备用触发和异常样本测试

- [ ] **Step 1: 将 OCR 降为备用方案**

  正常路径只使用高亮检测。仅当 ROI 位置有效但视觉分数连续不足时，才对对应键帽小区域执行 OCR；OCR 结果必须与行列位置一致才能采用。

- [ ] **Step 2: 记录必要诊断信息**

  每次异常记录：截图尺寸、ROI 比例、最高分键、第二高分键、分数差、连续帧数、当前状态和截图路径；不记录账号或其他敏感信息。

- [ ] **Step 3: 保存异常帧而非所有帧**

  只保存 ROI 无效、多候选、超时和输入后未变化的帧，避免日志和磁盘快速膨胀。

### Task 6: 离线验证和验收标准

**Files:**
- Create: 离线样本目录和测试数据说明
- Test: 钢琴识别单元测试、回放测试

- [ ] **Step 1: 建立最小样本集**

  至少包含：中音 `S` 高亮、其他 20 个键高亮、无高亮、两个键同时发光、动画过渡帧、亮度变化和 1920×1080/2560×1440 两种分辨率。

- [ ] **Step 2: 验证识别准确性**

  单键静态样本准确率目标不低于 99%；过渡帧不得产生连续错误按键；不确定样本必须返回暂停而不是猜测。

- [ ] **Step 3: 验证时序安全**

  同一高亮持续 500 ms 时最多发送一次对应按键；高亮变化后才允许发送下一次；异常退出后没有残留按键按下状态。

- [ ] **Step 4: 验证分辨率适配**

  在 16:9 分辨率缩放后，21 个检测框中心应落在对应圆点内，中心误差目标不超过圆点直径的 25%。

- [ ] **Step 5: 明确不纳入本阶段的内容**

  本方案不处理非 16:9 画面自动裁剪、不处理游戏窗口被遮挡、不处理网络延迟预测，也不通过游戏内部接口读取下一键序列。

## 验收结论

  当截图中中音区第二个圆点出现黄色光晕时，识别器应输出 `S`；当光晕消失或移动到其他位置时，必须等待新位置完成连续帧确认后再输出新键。任何无法确认的画面都应暂停输入并保留诊断信息。
