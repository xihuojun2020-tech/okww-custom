# 1.48.00 自动战斗异常与手动重启保护

## 已定位故障

2026-09-09 的 NAS 上传会话 `20260909-200505-3498bad879ca` 中，自动战斗在 21:43:36、21:44:03、21:44:16、21:44:33、21:44:40、21:44:51 共异常停止六次。主日志和错误日志为同一事件的双份记录，按时间去重。21:44:00 的重新启用记录与 21:44:03 的异常仅相隔约三秒。

共同异常为 `AttributeError: 'HavocRover' object has no attribute 'use_skyfall_severance'`。调用链为自动战斗、角色 perform、漂泊者气动流程。HavocRover 是漂泊者多形态共用实现，名称并不代表当时必须为湮灭形态。

队伍显示调用 `ensure_display_form()`，提前识别气动并写入 ring_index。原 `init()` 仅在 ring_index 未识别时调用 init_wind，导致队伍配合属性未初始化；框架捕获普通异常后 disable，因此每次重新启用仍会触发相同代码。修复为构造时提供默认值，并在每次气动初始化时重新计算队伍配合，不依赖形态识别发生的先后顺序。

## 使用规则

1. 普通开启、启动时恢复原开关，不启用保护。首次错误仍允许自动关闭，并显示原异常通知。
2. 因错误自动关闭后，通过程序自动战斗开关手动开启，启用本次程序运行的“手动保持开启”。界面刷新和普通 enable 调用不能冒充手动操作。
3. 保护期间再次异常，保留开关开启，结束当前动作、清理战斗状态，再以 2、4、8、16、30 秒间隔重新检查；后续最长 30 秒，不忙循环。
4. 窗口、截图或配置无效时等待条件恢复，不代表保持按键输入。仅释放自动战斗自己持有的按键和鼠标；释放失败时禁止新战斗动作。
5. 同一异常的完整日志最多每 30 秒一次，记录合并数量；状态记录恢复次数和最新异常。正常处理一次战斗后清除连续错误计数，但仍保留手动保护。
6. 手动关闭清除保护和等待状态；全局暂停不清除保护，但停止执行；退出和停止异常不被恢复机制吞掉。重新启动程序后保护重新建立，不保存到任务或账号配置。

不保证有代码错误时仍能完成战斗。保护表示不再替用户取消开启意愿，而不是无视错误继续盲目输入。

## 开发维护

- `HavocRover.init`：形态与队伍配合初始化分开，覆盖显示识别、协奏识别和队伍变化。
- `AutoCombatTask`：会话状态、明确的 UI 操作入口、单调时钟退避、输入释放与恢复状态。
- `TaskCard`：仅用户切换调用专用入口，程序化刷新仍使用 QSignalBlocker；头部显示手动保持开启或异常恢复中。
- `custom_ok/ok/task/TaskExecutor.py`：从当前框架实现建立覆盖；仅加入触发任务的可选 handle_execution_error 钩子与 retry_delay 调度。其他任务保持原异常处理。TaskDisabledException、FinishedException 优先走原控制分支，不进入恢复。
- 后续升级 ok-script 时应核对该覆盖与新版框架差异，不能只改虚拟环境内文件。
