# ok-script 框架升级说明与验收方案

日期：2026-09-11。本地产品本轮版本 1.57.00；框架仍固定 1.0.190。本次下载了 1.0.190 与 2.0.7b1 的官方 PyPI wheel 作离线源码、元数据比较，没有安装新版、修改依赖锁或运行游戏。

## 框架与我们的程序分别负责什么

ok-script 提供截图与设备连接、OCR、鼠标键盘输入、任务运行/暂停/停止、配置控件、界面和通知。我们的代码在其上实现鸣潮角色轮转、账号切换、每日任务、角色试用、完成证据和 NAS 更新等功能。

所以升级框架可能同时影响所有任务。原版 OK-WW 使用新版并不证明我们的定制界面与执行器兼容。反过来，角色头像和局部轮转可以在现有框架运行，不必以框架升级为前提。

## 已从安装包确认的变化

| 项目 | 1.0.190 → 2.0.7b1 的实际变化 | 对本项目的影响 |
| --- | --- | --- |
| 界面目录 | Qt 实现由 `ok.gui` 迁到 `ok.ui.qt` | 本地 25 份 custom_ok Python 文件中 21 份位于旧 GUI 目录，需要逐份映射；其中 LabelAndLabel 是本地扩展，新包没有同名实现 |
| 兼容导入 | `ok/gui/__init__.py` 用 MetaPathFinder 将旧导入指向新模块 | 旧 import 不必然报错，但本地复制覆盖及测试导入钩子可能与别名加载竞争，必须证明新旧路径得到同一类，且我们的代码确实生效 |
| UI 选择 | 增加 `gui.type=qt/web`，Web 支持 pywebview/browser/server；仍兼容旧 use_gui | 可以支持更多运行方式，但我们的 Qt 账号页和完成看板不会自动变成 Web 页面。本轮没有远程控制界面需求，不选 Web 路线 |
| 事件与翻译 | 执行器改用 `ok.core.events`、`ok.core.notifications`、`ok.core.translation`，locale 从配置读取 | 需要重新核对跨线程通知、任务状态刷新、五语言显示与 OCR 翻译；不能只替换 import 后认为完成 |
| 执行器退出 | 新增销毁互斥/幂等状态，工作线程改 daemon | 有改善退出卡住的价值；同时必须保证退出前输入释放、证据队列和配置保存没有丢失 |
| 主窗口退出 | 启动器关闭移到受锁保护的后台线程 | 有减少 GUI 退出阻塞的价值，应在本地退出场景验证，而非宣称一定解决现有问题 |
| 依赖拆分 | Qt、OCR、默认图像依赖、Web、ADB 等拆成 extras；Python 要求 >=3.11 | 本地 Python 3.12 满足最低要求，但只装裸包可能缺失 Qt/OCR/图像组件，必须按实际使用功能重新锁定依赖 |

比较依据是未修改的两个官方 wheel。当前 .venv 中若干文件已被本地启动流程覆盖，不能把它当作“原版 1.0.190”来统计差异。分析输出留在忽略目录 `test_out/framework-review/`，`mapped-overrides.json` 记录 25 项映射；其中 24 项在新版有对应文件，LabelAndLabel 需作为本地扩展保留。

## 必须保留的本地行为

1. **账号事务与输入边界**：UUID/别名/掩码身份核验、前台窗口与输入投递验证、失败重试、断点及队尾补跑。升级不能重置用户配置、替换账号选择流程或让测试使用另一套实现。
2. **自动战斗恢复**：本地 TaskExecutor 增加了触发任务异常处理与退避；直接使用上游执行器会失去这些扩展。需要迁移 handle_execution_error、retry_delay 等协议，并验证用户手动开启后的保护仍有效。
3. **完成证据**：本地执行器处理手动截图请求，任务仍向当前绑定 UUID 保存运行记录。新版暂停/退出路径必须明确处理在途请求；既有图片、历史和回收区不得因升级丢失。
4. **Qt 定制**：五页导航、默认折叠、独立开始按钮、统一配置控件、账号昵称/手机号显示、提醒及截图归属确认，均要以实际渲染和交互验证。
5. **截图与后台能力**：本地 windows_graphics 恢复及窗口判断扩展不能被覆盖；前台 BitBlt、后台截图、失去窗口、停止等场景分别验证。
6. **安装与更新**：主程序的 custom_ok 安装机制、测试的自定义导入钩子以及打包文件清单要同步迁移，防止开发环境通过而安装包仍加载旧目录。账号数据目录必须保持兼容。

## 推荐执行顺序

**阶段一：隔离基线。** 为框架迁移建立独立目录和虚拟环境，从官方 wheel 安装明确的 Qt/OCR/图像依赖，锁定所有版本；只使用合成配置和脱敏样本。保留现有稳定环境及安装包，不在 .venv 上直接 pip install -U。

**阶段二：启动和覆盖。** 在新版对应路径逐项迁移必要的本地差异，优先执行器、事件桥接、启动控制和配置控件，再处理账号/证据页面。统一新 import，验证旧兼容 import 与新路径的类对象一致，避免同一控件被加载两次。启动、关闭、重启及初始化失败恢复均需通过。

**阶段三：离线验证。** 运行完整测试，重点覆盖任务启停/异常退避、截图请求、UI 渲染、账号配置往返、旧数据迁移、包清单和升级配置保留。检查运行时加载模块的 __file__，不能仅验证目录里有覆盖文件。按模块修复真实不兼容，而非删测试或关闭功能来通过。

**阶段四：用户实机验收。** 由用户操作游戏，助手读取日志。先单任务启停及截图，再以生产 TestAccountSwitchTask 路径执行 A1→A3→A4，覆盖备用登录名和掩码手机号；然后验证每日、周本、试用、自动战斗异常恢复、后台捕获、证据截图和退出。每一步都确认无错账号输入、残留按键或丢失记录。

**阶段五：安装包与发布。** 在独立环境构建安装器，测试旧版→新版更新及回退。只有离线、实机与安装升级均通过，才更新主项目依赖锁并发布。若新版更改了数据格式，回退必须使用相应配置备份，不能只替换可执行文件。

## 是否值得现在升级

值得作为后续独立项目推进，主要价值是跟上上游维护、核心与界面解耦、退出流程改进及未来运行方式扩展；目前没有证据证明升级就会提高识别准确率、战斗效率或降低 CPU 占用。

**本轮建议保持 1.0.190，完成可独立吸收的功能。** 2.0.7b1 的 b1 表示框架自身为预发布版本，即使原版 OK-WW 将它用于稳定产品，也需要我们自己的验证。正式启动迁移时应重新检查框架稳定版与上游依赖，选择明确版本，不能长期盲目追踪 latest。

本次完成的是源码兼容性评估，不是新版启动测试、升级成功证明或未来实机验收。专项中的赞妮/菲比/光主回撤及图鉴校准仍按故障证据推进，不随本轮框架说明直接改动。
